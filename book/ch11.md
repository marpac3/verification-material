# 11. Assertion-Based Verification

Assertion-based verification expresses design rules as executable properties; this chapter explains their semantics and placement, how to assess their quality, and their use in simulation and formal proof. The opening example concerns a rule decidable from seven signals on one interface, which means those signals carry everything a check needs in order to judge it. In this example, the scoreboard reports a mismatch on the reference SoC: seed 4471 of the nightly regression copies 3 KB through a DMA channel into the neural accelerator's weight buffer, with eleven bytes at the wrong offset. The scoreboard is the structure that holds the data expected on an output and is consulted when that output is observed. A DMA channel is an independent transfer engine with its own registers and its own state, and the reference SoC's DMA has two of them, sharing one AXI backend. Two engineers spend a day and a half tracing the waveform backward because the scoreboard reports at transfer completion, some nine hundred cycles after the damage, requiring the entire interval to be retraced. The cause spans four cycles. The DMA offers an address with `AWVALID` on the crossbar port, and the subordinate delays acceptance. While that acceptance is pending, arbitration inside the DMA withdraws the address and offers a *different* one, and all of this happens before `AWREADY` returns. The subordinate had already latched the first one.

The failure is easy to detect but difficult to locate. The broken rule occupies one sentence of the bus specification: an offered address must remain offered and unchanged until accepted, and a check on the interface can detect the violation in the cycle it occurs. The missing check was an assertion stating that rule so a tool could evaluate it at the port.

The same assertion text can be sampled by a simulator and proved by a formal engine in Chapter 14 without changing a character.

## 11.1 Assertions as executable specifications

An assertion states a property of the design in positive form: what must hold, so that its falsehood indicates an error. An assertion is *declarative*: it specifies what to check and leaves the checking mechanism to the tool [cit:B4]. The declarative form distinguishes an assertion from a hand-written procedural checker, and it lets a single property of three lines serve a simulator, an emulator and a model checker without being rewritten for any of them. An emulator is a purpose-built machine that runs the design compiled onto a hardware fabric, and a model checker is a proof engine, the tool that decides a property over every legal execution instead of sampling it on one run.

The opening example uses the specification rule *the payload must remain stable while VALID is asserted and READY is low*.

<!-- slang: fragment - body of the deliberately wrong property p_aw_stable_wrong; the AW channel signals belong to the interface, not to this excerpt -->

```systemverilog
// Wrong: compares this cycle's payload against the previous cycle's.
property p_aw_stable_wrong;
  @(posedge clk) disable iff (!rst_n)
  (awvalid && !awready) |-> $stable({awid, awaddr, awlen, awsize, awburst});
endproperty
```

`$stable` tests whether a value is unchanged from the previous clock tick: at the observed stall, this property checks backward whether the payload was the same one tick ago. The obligation is forward, and it needs the non-overlapping implication, the operator that starts the consequent one tick after the antecedent rather than in the same tick:

<!-- slang: fragment - body of the corrected property p_aw_stable, shown without the module that would bind it to the interface -->

```systemverilog
// Right: the payload offered now must still be there at the next tick.
property p_aw_stable;
  @(posedge clk) disable iff (!rst_n)
  (awvalid && !awready) |=> awvalid && $stable({awid, awaddr, awlen, awsize, awburst});
endproperty
a_aw_stable : assert property (p_aw_stable);
```

The two versions differ by a cycle and one added term; the two edits serve different purposes. The cycle shift repairs a known mistranslation: "remain stable" in protocol prose means "hold the same value into the next clock cycle", and a bare `$stable` is a documented weakness of automated specification-to-property translation. A manager drives a fresh address in the same cycle in which it raises `AWVALID`. If `AWREADY` is low in that cycle, then the antecedent is true, `$stable` compares against the idle cycle before and is false, and the property fires on perfectly legal traffic. The property misses the opening example's withdrawal: when `AWVALID` drops, its antecedent becomes false and nothing is checked. The added `awvalid` in the consequent imposes a second rule, distinct from the first: an offer must not be withdrawn before acceptance. The documented stability fix is the cycle shift alone [cit:P12]; combining two obligations in one property is this book's explicit choice. {ref: sva_stable_backward} shows both defects.

```wavedrom
{ signal: [
  { name: "clk",                 wave: "p..............." },
  { name: "awvalid",             wave: "01..0...1.0....." },
  { name: "awready",             wave: "0..10..........." },
  { name: "aw payload",          wave: "x2..x...3.x.....", data: ["A", "B"] },
  {},
  { name: "awvalid && !awready", wave: "01.0....1.0.....", node: ".a........e....." },
  { name: "p_aw_stable_wrong",   wave: "x45x....45x.....", node: ".b........f.....",
    data: ["fires", "holds", "fires", "holds"] }
],
  head: { tick: 0 },
  edge: ["a-b same tick", "e-f no attempt"]
}
```

{figure: sva_stable_backward} Backward `$stable`: at cycle 1 a fresh address differs from the prior idle value and fires; at cycle 10 withdrawal leaves the antecedent false and nothing is checked.

Writing one requires naming the clock, the exact cycle relation, the condition under which the obligation starts, the reset behavior and the polarity of every term; each question must be answered from the specification or, when it is silent, from its owner. Chapter 5 treats an incomplete specification as a defect to expose; assertion writing exposes it because an unanswered question prevents completion of the property.

Because the language is declarative, debugging one is harder than debugging RTL: there is no statement to step through, only a verdict. Complex properties should be expected to be wrong on the first attempt, reviewed as carefully as design code, and drawn from a library for routine claims: "these two signals are mutually exclusive", "a request is granted within N cycles", "this state machine is never stuck" [cit:B4].

## 11.2 The anatomy of SVA

SVA semantics rest on four layers.

**The Boolean layer** uses ordinary SystemVerilog expressions over *sampled* values. A concurrent assertion is evaluated only at clock ticks, and the value it uses for a variable is that variable's value in the Preponed region: the value the variable held at the beginning of the time step that contains the clock edge, taken before the edge performs any update (IEEE Std 1800-2023, *IEEE Standard for SystemVerilog*) [cit:S8,B4]. An assertion therefore cannot race the RTL, cannot see a combinational glitch, and cannot be raced by the choice between blocking and non-blocking assignments. That choice still changes the design's behavior, and hence the value sampled at the next tick. Like a waveform reader, the assertion uses the value *before* the edge, so a property that looks off by one cycle in a debugger usually is not.

**The sequence layer** describes patterns over time, like a regular expression whose alphabet is Boolean expressions and whose step is a clock tick: `a ##1 b` is *b* one tick after *a*, `a ##[1:4] b` allows a window, `s [*3]` repeats. Sequences are why a temporal rule is three lines of SVA instead of the hand-written state machine protocol checking needed before the language existed. {ref: sva_sequence_ops} places the three on one timeline.

```wavedrom
{ signal: [
  { name: "clk", wave: "p............." },
  { name: "a",   wave: "010..10.......", node: ".p...r........" },
  { name: "b",   wave: "0.10....10....", node: "..q.....t....." },
  {},
  { name: "s",   wave: "0.........1..0", node: "..........u.v." }
],
  head: { tick: 0 },
  edge: ["p~>q a ##1 b", "r~>t a ##[1:4] b", "u<->v s [*3]"]
}
```

{figure: sva_sequence_ops} Three sequence forms: `a ##1 b` matches at cycle 2, `a ##[1:4] b` three ticks after a at cycle 5, and `s [*3]` from cycle 10.

**The property layer** turns sequences into claims, chiefly through implication. `antecedent |-> consequent` starts evaluating the consequent in the same cycle the antecedent completes; `|=>` starts it in the next. Two facts matter for Section 11.7: a false antecedent makes an implication succeed *without checking anything*, and antecedent selection changes what a pass means.

**The statement layer** supplies the four directives covered next: `assert`, `assume`, `cover` and `restrict`.

A concurrent assertion starts a fresh **evaluation attempt** at every tick of its leading clock; each reaches its own success or failure while overlapping others [cit:B4]. A five-cycle window permits up to five attempts in flight, so a violation under sustained traffic produces a burst of failures rather than one.

**`disable iff`** guards reset: while its expression is true, it discards any attempt in flight as *disabled*, neither pass nor failure. It is asynchronous, monitored at every time step rather than only at clock ticks, as asynchronous reset requires; this also exposes it to zero-width glitches unless explicitly sampled. There may be at most one per assertion, immediately after the clocking event, guarding the whole property [cit:B4]. Nearly every real property should carry one: reset violates almost every design rule, and repeated reset-time failures encourage disabling the suite. {ref: sva_disable_iff_reset} shows a discarded attempt.

```wavedrom
{ signal: [
  { name: "clk",         wave: "1010101010101010" },
  { name: "rst_n",       wave: "1......0....1...", node: ".......a........" },
  { name: "awvalid",     wave: "0...1...0...1..." },
  { name: "awready",     wave: "0..............." },
  {},
  { name: "a_aw_stable", wave: "x.....3.4.x...5.", node: "........b.......",
    data: ["in flight", "disabled", "holds"] }
],
  head: { tick: "0 . 1 . 2 . 3 . 4 . 5 . 6 . 7 . 8 ." },
  edge: ["a~>b discarded, no verdict"]
}
```

{figure: sva_disable_iff_reset} Reset falls between cycles 3 and 4, discarding the in-flight attempt rather than judging it; the attempt after release at cycle 6 holds.

**Immediate** assertions are procedural: they test a non-temporal expression when control flow reaches them, exactly like an `if`, and x, z or 0 counts as a failure. **Concurrent** assertions are the clocked, temporal ones [cit:S8]. If the claim is "this is true at this point in this code", it is immediate; if it involves a clock or spans time, it is concurrent.

<!-- slang: fragment - immediate and concurrent assertion excerpts; cnt and the clock come from the counter described in the text above -->

```systemverilog
// Immediate: a sanity check at the point where the value is computed.
always_comb begin
  a_imm_cnt_sane : assert (cnt <= 5'd16)
    else $error("count %0d exceeds depth", cnt);
end

// Concurrent: a rule about the design's behaviour over clock ticks.
a_conc_no_overflow : assert property (@(posedge clk) disable iff (!rst_n)
  (cnt == 5'd16) |-> (!push || pop));
c_cnt_full         : cover property (@(posedge clk) disable iff (!rst_n)
  cnt == 5'd16);
```

The immediate assertion describes the surrounding code, while the concurrent one describes the design and is checked on every test that runs, regardless of whether anyone remembers it. Its rule is the one Section 11.6 writes as `a_no_overflow`, there taking the push as the antecedent instead of the full condition; both reduce to *no push while full unless a pop retires in the same cycle*. The `cover` beside it applies Section 11.7's discipline from the first example onwards: an overflow rule on a FIFO that never fills has never been tested. {ref: sva_full_push_same_tick} reads the same-cycle exception off a trace.

```wavedrom
{ signal: [
  { name: "clk",                wave: "p..............." },
  { name: "push",               wave: "0.10.10.10......" },
  { name: "pop",                wave: "0....10........." },
  {},
  { name: "cnt == 16",          wave: "0...1.......0...", node: ".....a..c......." },
  { name: "a_conc_no_overflow", wave: "x....5x.4x......", node: ".....b..d.......",
    data: ["holds", "fails"] }
],
  head: { tick: 0 },
  edge: ["a-b same tick", "c-d"]
}
```

{figure: sva_full_push_same_tick} Same-tick consequent: push plus pop at cycle 5 holds at full, lone push at cycle 8 fails, and push at cycle 2 starts no attempt.

## 11.3 Assert, assume, cover: three claims about one property

The same property text can be attached to a design in four ways expressing verification intent: the three in the heading act in simulation, while a fourth is read only by a proof engine. `assert` makes the property an obligation on the design; `assume` makes it a constraint on the environment; `cover` monitors it for coverage; `restrict` constrains formal computation only, and simulators do not check it [cit:S8,B4]. The engine determines what each directive does; {ref: directive_semantics} compares the four for both engines, with the readings diverging at `assume`.

{table: directive_semantics} What the four property directives mean to each of the two engines that read them: the same property text attached as `assert`, `assume`, `cover` or `restrict`, with the simulator's reading in the middle column and the proof engine's on the right. The `assume` row is the one to read twice. In simulation an assumption is checked like an assertion; in formal it is not checked at all, it deletes from consideration every trace that violates it. An assumption written stronger than reality therefore deletes real traces too, and the proof result then describes a design that does not exist.

| Directive | In simulation | In formal verification |
|---|---|---|
| `assert` | fails if violated on this trace | proved, or a counterexample produced, under all stated assumptions |
| `assume` | checked like an assertion: a violation means the environment misbehaved | constrains the legal traces; its own correctness is *not* checked |
| `cover` | reports and counts each match on this trace | asks whether a matching trace exists, and returns a witness |
| `restrict` | ignored | constrains traces, like `assume` |

In simulation `assert` and `assume` are effectively synonyms: both are checked, and the keyword only identifies responsibility. In formal, assumptions are unchecked and delete traces; assertions are proved only over the remaining traces [cit:B4]. An assumption stronger than the real environment excludes legal traces from the proof. This asymmetry requires reviewing the directive alongside the property and motivates the assumption hygiene in Chapter 14.

When a module's interface obligations explicitly state its inputs' rules and its outputs' guarantees, integration mistakes turn into assumption violations on the first system-level run, and each violation appears at the boundary where the mismatch occurs [cit:B4]. The same rule is an `assume` when verifying the DMA in isolation and an `assert` when verifying the crossbar that feeds it.

## 11.4 Where assertions live

Assertion placement and authorship are two distinct decisions.

Assertions over internal signals require detailed knowledge of the design's internal structure, so the designer is best placed to write them; assertions over external interfaces treat the block as a black box, derive from the interface specification rather than the implementation, and are normally written by verification engineers [cit:B1]. Responsibility follows the source document rather than seniority: the designer uses the micro-architecture, the verifier the specification.

The designer's assertions belong inline in the RTL, next to the logic they constrain, because they must be maintained with that code. An assertion explains the logic in formal and natural language, as a comment would, and also reports when that explanation ceases to hold [cit:B1].

The verifier's assertions must not touch the RTL at all. SystemVerilog's `bind` construct instantiates a module, interface, program or checker into a target scope (every instance of a module, or one named instance) without modifying the target's source [cit:S8]. Interface assertions are attached that way, or placed inside the `interface` that carries the signals so they become part of its specification. Ownership becomes unambiguous: the RTL file is the designer's, and the checker bound into the design is verification's. A parameterized checker module is bound once to each of the crossbar's nine ports instead of copied nine times, and can be compiled out of a gate-level run under a macro [cit:B1].

One inline hazard illustrates Chapter 2's independence argument: an assertion written by the same person, in the same hour, from the same reading as the RTL encodes the same misunderstanding and never fires. Keeping implementation details from tainting the check requires explicit discipline [cit:B1]. The division of labor mitigates this: inline assertions state *implementation* invariants absent from specifications; bound assertions state *specification* obligations that no implementation should define.

## 11.5 Protocol checking: the interface as a contract

Protocol rules come from a public specification written by someone else, which provides an independent oracle, the mechanism that decides whether an observed response is correct. Protocol rules are local and decidable from one interface, so they are cheap to evaluate and within reach of a proof. Downstream diagnosis is expensive because a protocol error corrupts state whose effects surface much later elsewhere.

The distinction is between assertions on a *local* interface protocol and assertions on *end-to-end* behavior that relates one interface to another. The local ones are typically well suited to formal proof; the end-to-end ones usually span too much of the design for a proof and are often easier to express in the testbench. A check requiring extensive data structures or algorithms across much of the design belongs in a monitor and scoreboard (see Chapter 8) [cit:B1].
Siemens EDA's Verification Academy describes a monitor as doing three things: it reaches the design's signals through a virtual interface; it holds the code that decides when a run of signal activity amounts to a protocol pattern; and it broadcasts each recognized pattern as a transaction to whoever has subscribed [cit:B8]. A virtual interface is the reference through which testbench code reaches the signals of an interface instance.

### Worked example: the contract on a crossbar port

The reference SoC's crossbar has five manager ports and four subordinate ports. Each port carries an AXI4 contract (*AMBA® AXI and ACE Protocol Specification*, Arm IHI 0022H.c, 2021 [cit:S18]), and three of its clauses need visibly different amounts of machinery. The three are Arm IHI 0022H.c §A3.2.1 (handshake process), §A5.2.2 (write data ordering) and §A5.1 (AXI transaction identifiers), the last of which requires a Subordinate to reflect a Manager's ID on the corresponding BID or RID response.

**Clause one: handshake stability.** This is `p_aw_stable` from Section 11.1: while a request is offered and not yet accepted, it stays offered and unchanged. It needs no memory; the rule relates two adjacent cycles and SVA expresses it directly. {ref: sva_stable_forward} shows both outcomes.

```wavedrom
{ signal: [
  { name: "clk",                 wave: "p..............." },
  { name: "awvalid",             wave: "01..0...1.0....." },
  { name: "awready",             wave: "0..10..........." },
  { name: "aw payload",          wave: "x2..x...3.x.....", data: ["A", "B"] },
  {},
  { name: "awvalid && !awready", wave: "01.0....1.0.....", node: ".a.......c......" },
  { name: "a_aw_stable",         wave: "x.5.x....54x....", node: "..b.......d.....",
    data: ["holds", "holds", "fails"] }
],
  head: { tick: 0 },
  edge: ["a~>b one tick later", "c~>d one tick later"]
}
```

{figure: sva_stable_forward} Forward obligation: offers at cycles 1, 2 and 8 hold one tick later with the same payload; the cycle-9 attempt fails on withdrawal at cycle 10.

**Clause two: one burst's write data at a time.** AXI4 deprecated write-data interleaving, which AXI3 had permitted (Arm IHI 0022H.c §A5.2.2 [cit:S18]): a manager must issue its write data in address order; because no way is left to tag an interleaved beat, that rule means a manager finishes the data beats of one burst before starting another's; and an interconnect that merges writes from several managers must forward their data in the order in which it forwarded their addresses. The second obligation belongs to the crossbar in Section 11.5. AXI3's `WID` is gone, leaving no write-data ID to check; a counter and queue must reconstruct each burst and reconcile its beat count with the length promised by its opening address.

**Clause three: a response only for work in flight.** A write response may be returned only for an ID with an outstanding address, with no more responses than accepted addresses; this requires per-ID bookkeeping. {ref: sva_b_id_outstanding} shows the bookkeeping.

```wavedrom
{ signal: [
  { name: "clk",                wave: "p..............." },
  { name: "aw_hs",              wave: "01010..........." },
  { name: "awid",               wave: "x2x2x...........", data: ["k", "k"] },
  { name: "c_same_id_pair",     wave: "0..10..........." },
  { name: "id_out[k]",          wave: "23.4.3.2........", data: ["0", "1", "2", "1", "0"] },
  { name: "b_hs",               wave: "0....101010....." },
  { name: "bid",                wave: "x....2x2x2x.....", node: ".........a......",
    data: ["k", "k", "k"] },
  { name: "a_b_id_outstanding", wave: "5.........45....", node: "..........b.....",
    data: ["holds", "fails", "holds"] }
],
  head: { tick: 0 },
  edge: ["a~>b sampled one tick later"]
}
```

{figure: sva_b_id_outstanding} Per-ID bookkeeping: addresses at cycles 1 and 3 leave two writes under one ID; responses at 5 and 7 retire them, and response 9 has none to retire.

Clauses two and three require a *checker*: a small module with its own interface model, bound to the port. A property dependent on an implicit scoreboard is not reusable, so the checker's state must be explicit in its file.

```systemverilog
module xbar_port_checker #(
  parameter int unsigned IDW = 4,  // AXI ID width on this port
  parameter int unsigned AW  = 32  // address width
) (
  input logic           clk, rst_n,
  input logic           awvalid, awready, wvalid, wready, wlast, bvalid, bready,
  input logic [IDW-1:0] awid, bid,
  input logic [AW-1:0]  awaddr,
  input logic [7:0]     awlen,
  input logic [2:0]     awsize,
  input logic [1:0]     awburst
);
  wire aw_hs = awvalid && awready;
  wire w_hs  = wvalid  && wready;
  wire b_hs  = bvalid  && bready;

  // The checker's own model of the port.
  logic [7:0]  aw_len_q [$];    // AWLEN of each accepted address, in issue order
  int unsigned id_out [1<<IDW]; // writes outstanding, per ID
  logic [8:0]  w_beats;         // beats so far in the burst now on W (max 256)
  logic        len_err, id_err;

  always @(posedge clk) begin
    len_err = 1'b0;
    id_err  = 1'b0;
    if (!rst_n) begin
      aw_len_q.delete();
      foreach (id_out[i]) id_out[i] = 0;
      w_beats = '0;
    end else begin
      if (aw_hs) begin
        aw_len_q.push_back(awlen);
        id_out[awid]++;
      end
      if (w_hs) begin
        if (!wlast) w_beats++;
        else begin
          if (aw_len_q.size() == 0) len_err = 1'b1;       // data with no address
          else begin
            if (w_beats != aw_len_q[0]) len_err = 1'b1;   // wrong beat count
            void'(aw_len_q.pop_front());
          end
          w_beats = '0;
        end
      end
      if (b_hs) begin
        if (id_out[bid] == 0) id_err = 1'b1;              // response nobody asked for
        else id_out[bid]--;
      end
    end
  end

  a_aw_stable : assert property (@(posedge clk) disable iff (!rst_n)
    (awvalid && !awready) |=> awvalid && $stable({awid, awaddr, awlen, awsize, awburst}));

  a_w_burst_len : assert property (@(posedge clk) disable iff (!rst_n) !len_err);

  a_b_id_outstanding : assert property (@(posedge clk) disable iff (!rst_n) !id_err);

  // The covers that keep the assertions honest.
  c_aw_stall     : cover property (@(posedge clk) disable iff (!rst_n)
                     awvalid && !awready);
  c_w_overlap    : cover property (@(posedge clk) disable iff (!rst_n)
                     aw_hs && (aw_len_q.size() != 0));
  c_same_id_pair : cover property (@(posedge clk) disable iff (!rst_n)
                     aw_hs && (id_out[awid] != 0));
  c_max_burst    : cover property (@(posedge clk) disable iff (!rst_n)
                     aw_hs && (awlen == 8'd255));
endmodule
```

Every variable in the checker is written by this one block and read nowhere else except by the assertions, which sample in the Preponed region. The blocking style is safe here because every variable is owned by that one block, not because of the choice of assignment operator. Within a tick the statements run in the order written and the queue methods mutate immediately, so an address pushed at this edge is visible to the `pop_front` at the same edge, which makes a single-beat burst whose address and data arrive together check correctly. `w_beats` is deliberately one bit wider than `AWLEN`, so a manager that runs past its `WLAST` cannot wrap around onto a legal count. Because `len_err` and `id_err` are registered, an assertion samples them at the tick *after* the one that set them: the failure is reported one cycle behind the beat that caused it, with the transaction still on screen. {ref: sva_w_burst_len} shows that one-cycle offset on a burst that runs long.

```wavedrom
{ signal: [
  { name: "clk",           wave: "p..............." },
  { name: "aw_hs",         wave: "010....10.......", node: ".......d........" },
  { name: "awlen",         wave: "x2x....2x.......", data: ["1", "1"] },
  { name: "w_hs",          wave: "0..1.0...1..0..." },
  { name: "wlast",         wave: "0...10.....10...", node: "...........c...." },
  { name: "w_beats",       wave: "2..3.2...34.2...", data: ["0", "1", "0", "1", "2", "0"] },
  { name: "len_err",       wave: "0..........10...", node: "...........a...." },
  { name: "a_w_burst_len", wave: "5...........45..", node: "............b...",
    data: ["holds", "fails", "holds"] }
],
  head: { tick: 0 },
  edge: ["d~>c length compared at wlast", "a~>b sampled one tick later"]
}
```

{figure: sva_w_burst_len} Beats at cycles 3 and 4 match queued length; a third beat at cycle 11 sets `len_err` at `wlast`, reported at cycle 12.

Two instantiation lines attach the checker to all nine ports of the crossbar:

```systemverilog
bind xbar_manager_port     xbar_port_checker #(.IDW(4)) u_chk (.*);
bind xbar_subordinate_port xbar_port_checker #(.IDW(7)) u_chk (.*);
```

The five manager-side instances check the five managers. The four subordinate-side instances check the crossbar, which plays the manager role as far as a subordinate is concerned; this distinction determines how to interpret coverage below. The design source is untouched, and that file is what Chapter 14 hands to a proof engine. The two `IDW` overrides account for interconnect ID widening. An interconnect widens the ID it forwards, so a manager port carries the 4-bit ID the manager issued and a subordinate port carries a 7-bit one (Chapter 8 derives the three extra bits). Arm IHI 0022H.c §A5.2.3 [cit:S18] assigns the widening to the interconnect rather than the checker: "The ID identifier at a Subordinate interface is wider than the ID identifier at a Manager interface." `.*` connects only signals of the same name *and equivalent type*, so a checker at its default width fails elaboration on the subordinate side instead of silently misconnecting. Detecting this requires elaboration: lint is a structural check on the design description, which reports questionable constructs a compiler accepts, and lint alone does not resolve `bind`.

**Two limits of a passing check.** The four `cover` statements detect two different weaknesses.

The first is vacuity in the strict sense. `a_aw_stable` fires only when `awvalid &&!awready`, an offer that had to wait. If the subordinate models in the testbench accept every address immediately, that antecedent is never true, every attempt succeeds trivially, and the assertion reports a perfect record on a rule it never evaluated. `c_aw_stall` is exactly that antecedent, promoted to a coverage question: an empty `c_aw_stall` says the stability check has not run. {ref: sva_aw_stall_vacuity} contrasts a run without a stall against the first stall on the port.

{figure: sva_aw_stall_vacuity} Immediate acceptance leaves attempts vacuous and `c_aw_stall` empty; only the cycle-9-to-10 stall runs the check.

In the second case, the assertion evaluates but misses its intended hazard. In this example, an early sequence library issues one outstanding write per manager at a time, a reasonable initial choice that remains unnoticed once it works. The library belongs to bring-up, the phase in which the environment and the DUT first exchange checked transactions. `a_w_burst_len` still evaluates on every run and would still catch a short or long burst; what it never gets to see is the interleaving case it was written for, because on a manager port `aw_len_q` never holds two entries. After six weeks of nightly regression at 100% pass in this example, the hazard remains untested. `c_w_overlap` is the witness, and it reads zero. `c_max_burst` checks for acceptance of an address requesting the 256-beat maximum; without such a request, the beat-counting arithmetic is not exercised at that burst length.

The covers must be interpreted at their binding point. `c_same_id_pair` fires when an address is accepted whose ID already has a write outstanding *on that port*. On a manager-side instance it concerns one manager: a sequence library that cycles a fresh ID per transaction leaves the cover empty, while one that pins a single ID per manager fills it on every second outstanding write. On the four subordinate-side instances, this cover cannot detect two managers colliding on an ID. An interconnect that merges traffic *widens* the ID it forwards, appending enough bits to identify the source port so that no manager need know which IDs the others use; Chapter 8 does the arithmetic, four bits in and seven out. Two managers presenting `AWID` 3 reach the subordinate as two distinct IDs, so same-ID at a subordinate port still means *one manager*. The widening that renumbers those IDs leaves the crossbar with an ordering obligation: it must forward the writes that one manager issues under one ID in the order in which that manager issued them, and it must return their responses in that same order. This ordering is the obligation the cover witnesses there.

The other cover witnesses the crossbar bug's precondition. The canonical crossbar bug of this book is a violation by neither manager: each finishes one burst's beats before starting the next, exactly as clause two requires. The violation occurs on the subordinate side, where the crossbar must obey AXI: its write arbiter releases a burst's grant when the subordinate stalls the first data beat, so beats from two managers' bursts interleave on the write-data channel, and AXI requires the write-data channel's data to follow address order. On a subordinate-side instance, `c_w_overlap` witnesses *a second write address accepted while an earlier burst remains unfinished on the write-data channel*. This is the precondition; `a_w_burst_len` detects the failure because beats from two bursts counted as one match the queued head length only by coincidence. `aw_len_q` is keyed by arrival order alone, which is why an ID-based reading of this hazard finds nothing to check. `c_w_overlap` reads zero on these four instances too: the same sequence library leaves a different condition unmet. Filling it on a manager port takes one manager with two writes outstanding; filling it here takes two managers with writes in flight at one subordinate. A bring-up library exercising one manager against one subordinate, then the next pair, arranges neither condition. {ref: sva_w_overlap_precondition} shows the precondition and the failure it produces on one subordinate-side trace.

An antecedent cover quantifies whether the condition occurred. When a cover reads zero, two explanations require action: either no test drives the design into the situation, so the stimulus needs work, or the design can never reach it at all, in which case either the property is misformulated or something in the design prevents an expected state [cit:B4]. Section 11.7 turns this diagnosis into a general rule for writing assertions.

> **Scenario (elsewhere in the cast).** A 10G Ethernet MAC with time-sensitive-networking queues has a timing obligation: the reference design bounds the cycles from the start-of-frame delimiter to the frame's capture timestamp, and one hop exceeding that bound silently consumes the network's synchronization budget. Time-sensitive networking is the set of Ethernet extensions that give a chosen stream a bounded delivery delay. **Approach.** One assertion, and the cover that says whether a frame delimiter was ever seen at all:
>
> ```systemverilog
> a_ts_latency : assert property (@(posedge clk) disable iff (!rst_n)
>   $rose(sfd_seen) |-> ##[1:2] ts_captured);
> c_sfd        : cover property (@(posedge clk) disable iff (!rst_n)
>   $rose(sfd_seen));
> ```
>
> **Why.** `$rose` is true at a tick where the sampled value went from 0 to 1, so the obligation starts once per frame, and the window is the reference design’s specified timing budget, rather than a value inferred from the implementation. Deriving the obligation from the protocol specification keeps the check independent of the implementation. {ref: sva_ts_latency_window} shows one frame inside the window and one past it.

## 11.6 White-box assertions and internal invariants

Interface assertions check what the outside world is entitled to expect. Internal assertions check invariants that the implementation implies and the specification does not state, invariants that the designer knows and would otherwise record in comments. The standard catalogue covers state-machine transitions, memory access correctness, queue overflow and underflow, arithmetic overflow, and signal stability, though the complete list depends on the methodology [cit:B4]. {ref: sva_state_onehot} reads the state-machine invariant off a transfer.

```wavedrom
{ signal: [
  { name: "clk",             wave: "p..............." },
  { name: "state[0] IDLE",   wave: "1..0.......1.0.1" },
  { name: "state[1] ADDR",   wave: "0..1.0.......1.0", node: ".............a.." },
  { name: "state[2] DATA",   wave: "0....1...0...1.0", node: ".............b.." },
  { name: "state[3] RESP",   wave: "0........1.0...." },
  {},
  { name: "a_state_onehot",  wave: "5............4.5", data: ["holds", "fails", "holds"] }
],
  head: { tick: 0 },
  edge: ["a-b two bits set in one tick"]
}
```

{figure: sva_state_onehot} One bit is set through cycle 12; two at 13 and 14 fail the invariant; one returns at 15.

The DMA backend's datapath FIFO has 16 entries of 64 bits. The example checks four structural invariants, none derivable from the DMA’s specification:

```systemverilog
module dma_backend_invariants #(parameter int unsigned DEPTH = 16) (
  input logic                       clk, rst_n,
  input logic                       push, pop,
  // free-running binary pointers on a power-of-two depth: an index plus a
  // wrap bit, so their difference tells full from empty
  input logic [$clog2(DEPTH+1)-1:0] level,
  input logic [$clog2(DEPTH):0]     wr_ptr, rd_ptr,
  input logic [3:0]                 state  // one-hot: IDLE, ADDR, DATA, RESP
);
  a_no_overflow  : assert property (@(posedge clk) disable iff (!rst_n)
                     push |-> (level < DEPTH) || pop);
  a_no_underflow : assert property (@(posedge clk) disable iff (!rst_n)
                     pop |-> (level != 0));
  a_level_tracks : assert property (@(posedge clk) disable iff (!rst_n)
                     level == (wr_ptr - rd_ptr));
  a_state_onehot : assert property (@(posedge clk) disable iff (!rst_n)
                     $onehot(state));

  c_full         : cover property (@(posedge clk) disable iff (!rst_n)
                     level == DEPTH);
  c_full_bypass  : cover property (@(posedge clk) disable iff (!rst_n)
                     (level == DEPTH) && push && pop);
endmodule
```

Of the four invariants, `a_level_tracks` checks agreement between redundant state. The other three restate rules a careful designer already coded (`$onehot` is true when exactly one bit of its argument is set), while this one asserts *redundancy*: two independently maintained representations of the same fact, the occupancy counter and the pointer difference, must agree. Redundant-state invariants detect corruption affecting one representation while leaving the other unchanged, producing plausible-looking but incorrect data, six hundred cycles from its cause in this example. The equality holds because both operands are binary free-running pointers of the declared width, so their difference wraps modulo the pointer range. A gray-coded FIFO needs the synchronized binary shadow instead, because its pointers cross a CDC, a clock-domain crossing whose two clocks have no fixed phase relationship. {ref: sva_level_tracks} shows the counter moving without the pointers.

```wavedrom
{ signal: [
  { name: "clk",             wave: "p..............." },
  { name: "push",            wave: "0.10............" },
  { name: "pop",             wave: "0..............." },
  {},
  { name: "level",           wave: "2..3....4.......", node: "........a.......",
    data: ["k", "k+1", "k+2"] },
  { name: "wr_ptr - rd_ptr", wave: "2..3............", node: "........b.......",
    data: ["k", "k+1"] },
  { name: "a_level_tracks",  wave: "5.......4.......", data: ["holds", "fails"] }
],
  head: { tick: 0 },
  edge: ["a-b one representation moved alone"]
}
```

{figure: sva_level_tracks} Two representations of one fact: the push at cycle 2 moves both the counter and the pointer difference, and the counter alone advances at cycle 8, where the equality fails with no push and no pop to justify it.

The two `cover` statements apply Section 11.5: `push` and `pop` occur on any run moving data, so coverage must establish whether the FIFO reaches full. Of the two, `c_full_bypass` specifically witnesses `a_no_overflow`'s `|| pop` exception: a push accepted at full because a pop retires in the same cycle. A zero count means that exception remains unexercised and untested. The asymmetry with `a_no_underflow` is deliberate: this FIFO forwards a pop that arrives alongside a push at full, but does not forward a push to a pop at empty. {ref: sva_fifo_level_guards} shows the exception and the two failures on one trace.

Internal assertions improve observability, which is the basis of the partial-oracle role Chapter 3 assigns them: a partial oracle checks one projection of correctness rather than correctness itself. ### The property Chapter 14 will prove

One DMA backend rule is an interface obligation originating in the bus specification, but its violation comes entirely from the arithmetic of the burst splitter, the DMA stage that splits each transfer into bursts that the AXI address rules allow. Chapter 2 used that rule to show what an adversarial reading of a specification produces, and Chapter 3 used it as a worked case of what a partial oracle does and does not establish:


**Elsewhere in the cast.** Security rules are usually invariants over internal state rather than interface behavior, so internal assertions also express security properties. In the crypto engine, two assertions constrain key handling:

## 11.7 Assertion quality

Assertion-suite quality depends on how much of it could ever have failed rather than its size; three defects defeat that purpose.

**It never triggers.** A property `a |-> b` succeeds whenever `a` is false, establishing nothing: IEEE 1800-2023 §16.14.8 calls this vacuous and interprets it as not matching the user's intent, neither pass nor failure [cit:S8]. A run in which an assertion has only vacuous successes indicates one of two situations: either the tests never drive the design into the situation the antecedent describes, or the design can never reach it at all, in which case the property is misformulated or something in the design prevents an expected state [cit:B4]. **Every implication should have a `cover` on its antecedent**, written with the property and reviewed in the same review. For ordinary traffic, such as `push` on a FIFO pushing all day, a bare antecedent cover is insufficient. The rule should then be satisfied in one of two ways: by a witness that *implies* the antecedent and isolates the interesting case, as `c_full_bypass` does, or by the coverage model that Chapter 5's plan pairs with `p_no_4kb_crossing`. Chapter 6 reports these covers as assertion coverage; here they are required during property writing, before measurement.

Rule formulation also determines vacuity. `ok |->!err` and `err |->!ok` are logically equivalent but pass vacuously under opposite conditions: the first when `ok` is false, the second when `err` is false [cit:B4]. Antecedent selection therefore determines what a passing run means. The antecedent should be the rare, deliberately constructed condition, making a non-vacuous pass evidence and an empty cover an action item. {ref: sva_vacuity_polarity} shows the two passing vacuously on opposite stretches of one trace.

```wavedrom
{ signal: [
  { name: "clk",           wave: "p..............." },
  { name: "ok",            wave: "1.....0.......1." },
  { name: "err",           wave: "0..........1...." },
  {},
  { name: "ok |-> !err",   wave: "5.....3.......4.", node: "........a.....c.",
    data: ["pass", "vacuous", "fails"] },
  { name: "err |-> !ok",   wave: "3..........5..4.", node: "........b.....d.",
    data: ["vacuous", "pass", "fails"] }
],
  head: { tick: 0 },
  edge: ["a-b neither is checked", "c-d both fail"]
}
```

{figure: sva_vacuity_polarity} Two equivalent formulations on one trace: `ok |-> !err` passes on the stretch to cycle 5 and is vacuous from cycle 6, `err |-> !ok` is vacuous to cycle 10 and passes from cycle 11, and both fail from cycle 14.

**It restates the design.** An assertion derived from the implementation agrees with the implementation, including where the implementation is wrong; keeping the code from tainting the check is an explicit obligation on whoever writes an inline assertion [cit:B1]. In review, a property paraphrasing the `always` block six lines above it, with the same signals in the same order, reveals this defect. The remedy is Chapter 2's approach: derive the property from the specification's *prohibition* rather than the implementation mechanism.

**It cannot distinguish anything.** Each assertion review should identify one RTL mutation that the assertion catches and code coverage does not. The mutation is a small deliberate change to the design code, introduced to see whether a check notices it. Without such a mutation, the assertion adds runtime cost without distinguishing behavior. Counts of signals touched or assertions relative to code size are legitimate structural indicators of effort [cit:B4]; they should not become goals. A suite of two hundred properties that restate a register decode, with none on the ordering rules, is worse than a suite of twenty placed where the risk analysis said the design was novel.

## 11.8 The same text, two engines

One of the stated goals of SVA is a common semantic meaning, so that a single property can drive different classes of design and verification tool [cit:S8]. That is why the checker in Section 11.5 is a deliverable rather than a simulation artifact. Three semantic changes must be understood to interpret proof results correctly.

**Assumptions stop being checks.** The first of the three is Section 11.3's asymmetry: assumptions are checked in simulation but never in formal, where they delete traces. Simulation setup builds the environment; formal setup states assumptions, and a missing assumption produces spurious failures rather than a silent gap [cit:B4].

**Covers stop counting and start searching.** A `cover` in simulation reports how many times the scenario occurred on this trace; in formal it asks whether the scenario is reachable at all and returns a witness if it is [cit:B4]. An empty cover means either "no test produced it" or "no legal execution can produce it": two different conclusions, only the second about the design.

**Liveness becomes decidable.** The property `req |-> ##[1:$] gnt` requires the eventual grant of a request, and it cannot fail in simulation: its attempt remains open until the run ends, and because many open attempts degrade performance, simulation properties should bound open-ended intervals with other operators [cit:B1]. A proof engine decides the same text. This rule can be written in the common language but answered only by proof; the usual simulation compromise is a bounded restatement (`##[1:16]`), not equivalent to the liveness rule but falsifiable in a finite run. {ref: sva_liveness_bounded} shows the two forms on the same pair of requests.

```wavedrom
{ signal: [
  { name: "clk",                    wave: "p..............." },
  { name: "req",                    wave: "010.....10......", node: ".a......c......." },
  { name: "gnt",                    wave: "0...10..........", node: "....b..........." },
  {},
  { name: "req |-> ##[1:$] gnt",    wave: "x3..5x..3.......",
    data: ["open", "holds", "still open"] },
  { name: "req |-> ##[1:16] gnt",   wave: "x3..5x..6.......", node: "........d.......",
    data: ["open", "holds", "fails past this window"] }
],
  head: { tick: 0 },
  edge: ["a~>b granted within the run", "c-d deadline set here"]
}
```

{figure: sva_liveness_bounded} Both forms on one pair of requests: the request at cycle 1 is granted at cycle 4 and both hold, while the request at cycle 8 leaves the unbounded attempt open to the end of the run and gives the bounded form a deadline.

The coherent hub illustrates the distinction. The hub is the block that keeps several caches in agreement about the copies they hold of one memory line. Its invariant requires that at most one cache may hold a line in the Modified state, the state of a line whose only current copy sits in that one cache and may be written there:

<!-- slang: fragment - assertion a_single_writer shown alone; modified_vec is the coherent hub's internal state vector, described in the text above -->

```systemverilog
a_single_writer : assert property (@(posedge clk) disable iff (!rst_n)
  $onehot0(modified_vec));
```

Every system-level simulation of the hub samples this invariant, and Chapter 14 proves it over the hub's canonical protocol abstraction of two caches and one address: `modified_vec` is the per-line vector of Modified holders, and `$onehot0` is true when at most one of its bits is set. The two engines use the same text; only proof establishes the invariant for the stated protocol abstraction. {ref: sva_single_writer} shows the tick at which the invariant fails.

{figure: sva_single_writer} The invariant across two caches: at most one bit of `modified_vec` is set from cycle 0 to cycle 8, both are set at cycle 9, where the assertion fails, and one holder remains at cycle 10.

A 2024 framework for producing SVA from a full natural-language specification reported 89% of its 56 generated properties correct both syntactically and functionally on a single serial-bus design; *correct* there means that the property passed a formal proof against a known-good RTL, and the score was taken after human engineers had removed the generations that referenced signals the tool could not map [cit:P11]. Under this definition, a property with an unreachable antecedent also passes proof on bug-free RTL and would score as correct, the issue in Section 11.7. The result does not yet establish a trend, and its correctness criterion does not establish that a property checks the intended behavior. Section 11.1 illustrates the translation failure: protocol documents address experienced engineers and are ambiguous by machine standards, so automated translation chooses an intuitive operator with the wrong cycle relation [cit:P12]. The corpus also reports an earlier, narrower result on designs available to download and re-run: the taped-out open-source Ariane (CVA6) core and the OpenPiton manycore framework. In those two hierarchies, 236 liveness and safety properties generated from 110 lines of interface annotation ran across seven forward-progress-critical modules. The properties proved out on the page-table walker and the translation-lookaside buffer after roughly 30 minutes of human effort spent defining the correct transactions; the same generated set found real bugs in the memory-management unit and in an OpenPiton network-on-chip buffer, and both of those modules then proved in full [cit:P15]. Transaction annotations are far less ambiguous than protocol prose, which makes the generated properties checkable. Generation should serve as a drafting aid, with its output receiving the same review as hand-written properties.

### In practice

Two streams of assertion development should meet at integration. Inline assertions should accompany RTL commits and first be used in the designer's unit runs. Protocol checkers should be written from the interface specification during planning and bound at bring-up; in this example, most of their bug-finding occurs in the first two weeks. Chapter 5's plan fixed the `p_no_4kb_crossing` binding point, the backend's AXI write-address channel, before the checker code was written.

If a noisy assertion is disabled with a plusarg and left disabled, failure counts must be audited against the enabled list rather than the file. A plusarg is a switch the simulator takes on its command line, read by the code as the run starts. Assertions in gate-level or emulation runs have to be compiled out or restructured, which is why the macro guards exist. Emulation is the run of a design compiled onto a hardware execution fabric, under stimulus a host supplies. A bound checker with state is software and needs review for its own bugs; if its first week finds more defects in the checker than the design, that alone does not invalidate it.

### Pitfalls

1. **No `disable iff`.** Symptom: repeated failures during the first twenty cycles of every test teach users to ignore the suite. Cure: guard every concurrent property with the reset condition, once, immediately after the clocking event.
2. **The assertion that was never in a position to fail.** Symptom: 100% pass rate beside an empty antecedent cover. Cure: write the cover with the property, and treat an empty one as a stimulus bug until proven otherwise.
3. **An implication pointing the wrong way in time.** Symptom: the same timing mistake has two manifestations, failure on legal traffic or silence on the intended scenario. Cure: check the cycle relation explicitly (`|->` is the same tick, `|=>` the next) and confirm on a waveform which direction `$stable` checks.
4. **The property that paraphrases the RTL.** Symptom: assertion and logic use the same signals in the same order, written in the same hour. Cure: derive from the specification, and state the prohibition rather than the mechanism.
5. **Unbounded eventuality in simulation.** Symptom: a liveness property that has never failed and never will, plus a slow regression from thousands of open attempts. Cure: bound the window for simulation, send the unbounded form to formal.
6. **Assertion count as a goal.** Symptom: a metric rising steadily with no movement in the bug curve, the plot of bug discoveries over time. Cure: measure where the assertions are against where the plan said the risk was.

### Summary

- An assertion declaratively expresses a specification in the precise form a tool can evaluate [cit:B4]. Writing one exposes ambiguity in a specification sentence.
- Concurrent assertions are clocked and use sampled values from before the edge, so they cannot race the design; `disable iff` discards in-flight attempts asynchronously and belongs on essentially every property [cit:S8,B4].
- `assert`, `assume` and `cover` are three intents over one property text. In simulation the first two are the same check; in formal an assumption is never checked and instead deletes traces [cit:B4].
- Interface assertions come from the specification and attach with `bind`, keeping verification code out of the design; internal invariants come from the micro-architecture and belong inline [cit:B1,S8].
- White-box redundancy assertions check agreement between two representations of one fact, detecting silent corruption that affects only one.
- For an implication, an antecedent cover distinguishes exercised checks from vacuous successes [cit:S8,B4].
- The same text is sampled by a simulator and proved by an engine, but assumptions, covers and liveness all change meaning between them (Chapters 14 and 16).

### Further reading

Within the corpus, [cit:B4] treats SVA semantics: assertion kinds and evaluation attempts, sampled values and reset, assumptions and coverage as first-class directives, checkers and checker binding, with the fullest available discussion of vacuity. IEEE 1800-2023 [cit:S8] is definitive on the four directives, on sampling, on non-vacuous evaluation and on `bind`. For methodology, the assertion chapter of [cit:B1] covers authorship, inline versus bound placement, reusable checker packaging and coding rules for simulation performance; [cit:B2,B6] place assertions among the other oracles. On automated property generation, [cit:P11] reports the state of specification-to-SVA generation as of 2024 and [cit:P12] documents why protocol documents in particular defeat it; [cit:P15] is the corpus's account of generated liveness and safety properties run against taped-out open-source silicon.

Outside the corpus: H. Foster, A. Krolnik and D. Lacey, *Assertion-Based Design*, is the standard book-length treatment of assertion methodology; the Accellera Open Verification Library remains a readable model of how a reusable checker library is packaged and parameterized.
