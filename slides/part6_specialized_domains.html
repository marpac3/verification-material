A HOLISTIC GUIDE4

Chapter 21 · Where the abstraction stops

Three engineers spend a week looking for the bug. There is no bug.

assert (adc_code == expected_code);

It fails on nearly every run — not by much: one code, occasionally two. One least-significant bit against the analog front-end's 1.8 V reference is 1.8 / 4096 ≈ 439 µV, and 439 µV is smaller than the amount by which the model, the schematic and the eventual silicon are designed to disagree. The comparison was never going to hold.

What happens next is the real defect Someone changes the check to ±2 LSB, the regression goes green, and the number is never written down anywhere but that line of code. Six months later a run fails at 3 LSB and nobody can say whether that is a bug, a modelling artifact, or an unlucky seed — because nobody knows where the 2 came from. A debugging convenience has quietly become the specification.

SayThe instinct to widen the check is correct. Everything wrong here happens in the ten seconds after it.

A HOLISTIC GUIDE5

Chapter 21 · The oracle

The verdict has three parts where a digital verdict has one

Part of the verdictWhat it fixes, and what goes wrong without it
A bandAbsolute (± 10 mV) or relative (± 2%) — and the choice is a trap in both directions. Next slide.
A windowAnalog outputs settle. A comparison made before the settling time has elapsed is checking a transient; one made at an arbitrary time is checking whatever the model's step size happened to produce. Every analog check needs a stated moment or interval at which it is valid.
A condition setSupply voltage, temperature, process corner, input frequency, load. A tolerance without the conditions under which it holds is not a specification.
Scenario · the same four fields, as a plan row The PLL must be within 100 ppm of target after lock. The row states the band (100 ppm), the window (1024 output cycles beginning 20 µs after the lock request), the conditions (nominal supply, three temperature points, three process corners), and the source of the band — the tightest frequency accuracy any consumer of the system clock demands. The checker reads all four from a package, not from literals. Why: when a run fails at 140 ppm the conversation is about which requirement is violated and whether the band or the design should move. Without the row it is about whether 100 was ever the right number, and it has no ending.

A digital plan row closes when a coverpoint is hit or an assertion is proven. A mixed-signal row closes when a measured quantity sits inside a stated band under stated conditions, with a named source for the band. Scattered as literals through the testbench, those numbers leave the team unable to answer the two questions that matter in a bring-up crisis: where did this tolerance come from, and who approved it.

SayThose PLL numbers are that chapter's illustration, not a house constant. What transfers is the four fields, and that the fourth one is a name.

A HOLISTIC GUIDE6

Chapter 21 · The oracle

A band is only as meaningful as the thing it is a percentage of

package afe_spec_pkg;
  // Bands for the front-end: one place, one owner,
  // quoted everywhere.
  localparam real V_REF = 1.8;   // reference, volts
  // Model-vs-schematic band: 1% of FULL SCALE, named
  // in register row MDL-AFE-ADC-01.
  localparam real V_CORR_ABS = 0.01 * V_REF;
endpackage

// Correlation runs only: model vs transistor level.
always @(posedge sample_done)
  if (corr_run && !(v_mdl inside {[v_ckt +/- V_CORR_ABS]}))
    $error("AFE model outside its correlation band");

The correlation check uses the absolute token, and that is the whole argument. A band taken as a percentage of the measured value shrinks with the signal and collapses near zero. The same percentage of the fixed full-scale reference is a constant band across the whole range.

And the trap runs both ways An absolute tolerance on a quantity that legitimately spans three decades is meaningless over most of its range. The reference point is a choice with a failure mode on each side — so state which one you picked, and against what.

Coverage inherits the same problem. A bin naming a single real value can fail to be hit at all, because floating point has limited precision: 0.1 + 0.2 yields 0.30000000000000004, which is not in a bin covering {0.3}. A tolerance token attached to a single value defines an implicit range a real measurement can land in.

SayNone of those numbers is a bare literal. Each is a named constant with a comment, and the correlation band names the model-register row behind it — which is the entire point. corr_run keeps the nightly regression and the correlation campaigns apart in one file.

A HOLISTIC GUIDE7

Chapter 21 · Real number modelling

No matrix solve, therefore no convergence failure — that is the whole value proposition

An analog model describes the current-versus-voltage relationship between nodes, and the solver finds all node voltages and branch currents by Newton–Raphson iteration with matrix inversion, choosing each timestep from accuracy criteria. A real model has no matrix solution at all: the output is computed directly, the model itself decides when to perform each internal computation, and there is no continuous-time operation — only sampled, clocked or event-driven updates, inside the ordinary event-driven simulator.

A HOLISTIC GUIDE8

Chapter 21 · Real number modelling

Speed is bought with abstraction — know exactly what left the building

Electrical relationshipsA real net carries a value, not a Kirchhoff relation. Loading, drive strength, input impedance and current draw are simply absent unless the modeller writes them in. A shared bias line feeding two loads behaves in a real model exactly as it would with one — which is the point at which a whole class of real circuit failures becomes invisible.
Continuous timeThe model updates on events; between updates the quantity is a held value, and any transient shorter than the update interval does not exist. Glitches, ringing, overshoot on a supply ramp, and the settling behaviour a tolerance window is supposed to be checking, appear only if the modeller decided in advance to represent them.
Noise, variation, marginThermal noise, jitter, offset, mismatch and the spread across process corners are not free consequences of a real model the way they are consequences of a circuit. Each one is a feature somebody wrote, with parameters somebody chose.
Not an argument against the technique The alternative to abstraction here is not simulating everything — it is simulating nothing. It is an argument for enumerating which of your checks depend on the discarded physics, because those checks are checking the model rather than the design.
Scenario · the radar receive chain, and its stated limit A real model of the analog path lets the testbench generate the chirp: sweep return amplitude across the full input range, inject a controlled noise floor, drive the amplifier into and out of saturation, run it as a constrained-random regression. The limit: the model's noise floor is a parameter, not a measurement, so a detection threshold tuned against it has been tuned against a cleaner world than the silicon.

SayThat last sentence is the whole of the next three slides in miniature. The number needs a source, and the source is a correlation run.

A HOLISTIC GUIDE9

Chapter 21 · AMS co-simulation

Co-simulation is a campaign, not a regression tier

One simulation, two solvers exchanging values at their shared boundary; where a continuous discipline meets a discrete one, connect modules are inserted automatically. Every time the digital side wants an analog value it must ask the analog solver to interpolate one, and that request is blocking: control passes to the analog solver and does not return until the value is available. A sampling clock chosen without thought does not merely add work — it repeatedly stalls the digital engine on the slowest component in the system.

The rule that survives contact with a schedule Co-simulate what real number modelling threw away, and nothing else.
  • Model correlation runs — the most valuable use, because it is what makes every subsequent real-model run mean something.
  • Failures that live in loading, current and impedance — precisely the class a real model cannot express and therefore cannot fail on.
  • Power-up, power-down, supply ramps.
  • One end-to-end signal-path scenario per configuration — not for bug-finding, but as evidence that the composed system behaves as the real models claim.
Scenario · the sensor hub's shared bias reference Two channels, one bias reference, firmware may enable them independently. The real model of the bias generator delivers its nominal output regardless of how many channels are enabled, so a real-model regression will never show a problem. One co-simulated scenario enables both and checks the reference under the doubled load. The failure is a droop that shifts the first channel's conversion beyond its stated tolerance — a loading failure by construction, invisible to any abstraction that does not carry current. What it costs: one scenario, re-run when the bias generator's schematic changes. Not nightly.

Read the previous slide's table backwards for the magnitude: 0.4 s against 92.5 s. At anything like that ratio an hour of real-model regression becomes a multi-day proposition, and a job that had to finish overnight does not finish at all.

SayThe memory PHY's training, owed from Part V: the AMS boundary can discharge the algorithm — convergence against a channel model, termination rather than looping, reachable retry and fallback paths, timing obligations throughout. It cannot discharge the distribution of training outcomes across parts and temperature, which does not exist until there are parts. Two rows; the second closes in the lab.

A HOLISTIC GUIDE10

Chapter 21 · The trust problem

In analog the schematic is the reference — and nothing mechanically checks the model against it

A model nobody has correlated is a lie you regress against nightly — an expensive one, because it produces green results, at speed, in volume, for months.

Digital

The specification is the reference and the implementation is checked against it. That is what makes a golden model golden in this book's vocabulary: it is golden because it is the specification. Synthesis then produces the gates, and equivalence checking closes the RTL-to-gates gap mechanically.

Analog

The direction reverses. The schematic is treated as the reference — golden because it is what gets fabricated. There is no analog synthesis, so the schematic is a creative artifact rather than a derived one, and there is no equivalence checking to confirm that a hand-written model matches it.

Which relocates the whole problem Digital's risk is a misinterpreted specification, which is why the discipline puts two independent pairs of eyes between specification and RTL. Analog specifications are usually interpreted correctly and are quite simple; the problems are creating the implementation and creating the model. So analog's second pair of eyes is not an assertion in a testbench — it is the comparison of two independently created representations of the same block, the schematic and the model.

SayChip-level verification assumes correlated models. Without them, chip-level verification is suspect — and it will not look suspect, because it will be green.

A HOLISTIC GUIDE11

Chapter 21 · The trust problem

Correlation is a procedure with an artifact — and its result expires

The procedure

  1. One self-checking testbench, written against the block's specification.
  2. Run twice — once against the behavioural model, once against the schematic at transistor level.
  3. Compared per port, against a declared tolerance. In a published programmable-gain-amplifier example: output voltage within 10 mV, supply current on the supply pin within 1 mA. The third point is where most teams fall short: the correlation tolerance is part of the specification, per port, before anyone runs anything. A match criterion invented after seeing the mismatch is not a criterion.

The model register — one row per model

Re-correlate whenThe schematic or specification changes; a new operating condition is used; a parameter changes with no schematic change; or a model is edited during debug — the most dangerous, because it happens under pressure and makes a failing test pass

SayThe last three rows are what make the register worth maintaining. A date turns “the model is correlated” into a claim that can visibly go stale, and the consequence field lets a reviewer ask the only question that matters about a model: if this is wrong, what else is wrong with it?

A HOLISTIC GUIDE12

Chapter 21 · The boundary

You are almost certainly not verifying the analog block. Name what you do own.

The interface contractEvery control line's meaning, every status line's timing, the register map, and the wiring — supply lines, current bias lines, voltage references, and at chip level thousands of digital control lines into the analog domain. A swapped or inverted control line here produces a plausible-looking analog output rather than an obvious failure.
The control and calibration sequencesTrim searches, offset cancellation, lock acquisition, gain ranging. Pure digital logic operating on analog feedback — and the only part of the system whose correctness depends on both a state machine and a tolerance.
The failure handlingWhat the design does when the analog reports out-of-range, fails to converge, or saturates. A must-not-happen class, systematically under-verified here because the failure conditions are ones the model must be told to produce.
The tolerances themselvesNot the physics behind them — their provenance. Every band in the plan traceable to a specification, and the model register kept current.
Scenario · a third currency, on the flash controller Read-retry walks a table of reference-voltage offsets. The correctness questions are entirely digital: the table is applied in order, the retry budget is respected, and exhausting the table reports an uncorrectable error rather than silently returning the last attempt. But the oracle is a probability, not a band: with correction downstream, a marginal read is not wrong, it is more likely to need correcting. The row closes on a bit-error-rate distribution — a third currency after equality and tolerance, and a reason to name the currency explicitly in every mixed-signal plan row.

SayThe sensor hub's wake-up trim search is the second row made concrete: verify the search, not the sensor. Does it terminate for every starting code? What does it do when two codes tie? What happens when the reading never settles — does it converge on a wrong code, or report failure? The trap: a search that always converges in the model may be relying on monotonic behaviour the real sensor does not guarantee — a modelling assumption, and it belongs in the register with the model that carries it.

A HOLISTIC GUIDE13

Chapter 21 · In practice

Two populations, a supply randomised wider than legal, and an owner for each half

Two populations, not oneA nightly regression built entirely on real number models, and correlation campaigns fired by the named triggers. Mixing them produces a nightly job too slow to be nightly, and a correlation result nobody can locate.
Randomise the supply, and cover itThe highest-value analog coverage habit. In a published fractional-N PLL case: nominal 2.5 V, randomised across ±7% — deliberately wider than the ±5% legal band — with three coverage bins, an under-voltage region below 2.375 V, a healthy band from 2.375 V to 2.625 V, and an over-voltage region above. Twenty runs then produce a report that shows whether the supply ever left its healthy band. The numbers belong to that design; the habit is what transfers — and a team that has never asked the question is usually surprised by the answer.
Split ownership from accountingThe analog engineer writes and correlates the model; the verification team owns its row in the register and its expiry. Neither role works alone: the writer does not see the chip-level runs that depend on it, and the accountant cannot judge whether the physics is right.
The economics, as a shape rather than a budget line One consultancy's experience across many mixed-signal chips puts creating correlated analog functional models at as much as 80% of the effort of getting analog blocks into chip-level verification, and analog verification as a whole at typically 20% of the design effort — rising to 30% or 40% for a team new to it. The same source puts the proportion of analog designers skilled at reading models at around 20%, with fewer able to write them. These are experiential figures rather than survey data and they carry no year: treat them as the shape of the problem.

SayThat skill distribution is why ownership needs an artifact rather than an org chart. The person who can tell whether the model is right is not the person who notices when it is wrong.

A HOLISTIC GUIDE15

Chapter 22 · What changes

Every plan row discharged, coverage closed, regression green — and the first question is about none of it

Eleven weeks before tape-out, at the end of the table “Your architecture says the tightly-coupled memory is protected by single-error-correcting, double-error-detecting code, and that a double-bit error is reported to the safety island inside the fault-tolerant time interval. Show me the faults you injected into that path. Show me the ones the mechanism did not catch. And show me your argument for why the faults you did not inject did not need injecting.”

Nobody in the room can answer, because nobody was asked to. The error-correcting code was verified the way every other block was — correct data in, correct data out. A perfectly good functional argument, answering a different question.

ProcessActivities have prescribed inputs and outputs, reviews prescribed independence, changes prescribed impact analysis. You can no longer quietly delete a test that has become useless, quietly re-scope a coverage model, or quietly upgrade a tool.
EvidenceGreen is a state; evidence is a retained state — tied to a specific design revision and tool configuration, with the raw results kept and not just the summary. From we ran it to we can show, later, what we ran and what came back.
TraceabilityForward from every safety requirement to the thing that discharges it, and — the direction most teams never build — backwards: given a test, name the requirement it serves. A test that traces to nothing is an unexplained artifact in a controlled repository.
And the consequence that outranks all threeThe argument itself becomes a deliverable. You are no longer producing results — you are producing the premises of somebody else's argument, and you will be asked whether each premise says what the argument needs it to say.

SayIn 2024, 44% of IC/ASIC projects worked to at least one safety-critical standard or guideline, 63% on FPGA; among those that do, the median spends between a quarter and half of total project time on functional-safety activities. And what teams themselves name as hardest is safety architecture and requirements traceability — ahead of fault list generation and injection. The technique is not the bottleneck; the bookkeeping around it is.

A HOLISTIC GUIDE16

Chapter 22 · The organising distinction

A design can be perfectly correct and still kill somebody

Systematic fault — a design bug

A mistake made during development, present in every part ever manufactured, and always permanent. Constrained-random stimulus, formal proof, coverage closure, regression engineering, gate-level simulation, post-silicon bring-up: almost everything in Chapters 1 to 21 is aimed at this. A safety standard demands that work too, with more process around it.

Random hardware fault — a physical defect

A latch-up, a marginal via, an aging transistor, a particle strike. Arising during manufacturing or in operation, and either permanent or transient. You cannot verify it away. It is a physics problem, and the physics will happen at some rate whatever you do.

Which is why this work feels alien What you can do is show that when it happens, the design notices and does something safe. For the first time you are not hunting a bug — you are measuring a mechanism's effectiveness against a population of defects that are nobody's fault.

SaySafety verification does not replace functional verification. It adds a second target, and the second target has no bug at the end of it.

A HOLISTIC GUIDE17

Chapter 22 · Where your target comes from

You inherit a target — and where no mechanism exists, no campaign can improve its coverage

An ASIL — automotive safety integrity level, A through D, with D the most demanding — is not a property of your block. It is arrived at by assessing the risk of a potential hazard, weighing three judgments: how severe the harm would be, how often the vehicle is exposed to the situation, and how well a driver could control the outcome. A headlamp that fails on a lit motorway and one that fails on an unlit country road are the same electronics and different hazards. The level then travels down — hazard, safety goal, system requirements, requirements on your part, requirements on your block — and by the time it reaches you it is a number in a requirements document. You almost never get to argue about it.

Scenario · the reference SoC has nothing to measure No error-correcting code anywhere. Its 512 KB of tightly-coupled SRAM is fast, four-banked, and completely undefended: a particle strike that flips a bit in a weight buffer produces a wrong answer with no indication that anything happened. That was a defensible choice for a low-power edge part whose worst failure is a wrong inference. The answer is not to bolt detection onto it — it is a derivative, the flagship-A, with error-correcting protection on the tightly-coupled memory, the L2 slices and the memory path, a dual-core delayed-lockstep safety island, and monitored reset and clock.
Detection is architecture, not a verification add-on There is no fault campaign you can run on the reference SoC that will improve its diagnostic coverage, because it has no mechanism whose coverage could be measured. This is the first judgment call of a safety project and it happens before verification starts: if the failure analysis says a failure mode needs covering and no mechanism covers it, the finding is a design finding — and the later you raise it, the more expensive it is.

SayOne structural fact about the flagship-A, because it recurs: the safety island is built to ASIL D inside a system built to ASIL B. Different parts of one chip carry different targets, and the boundary between them is itself something you verify — a fault in the ASIL B region must not defeat the ASIL D region's mechanisms. That is the reason the safety island exists as an island.

A HOLISTIC GUIDE18

Chapter 22 · Failure analysis as an input

The failure analysis is a verification input, not a document to file

A failure mode, effects and diagnostic analysis works element by element and asks a fixed set of questions of each: in what manner can this element fail; what is the consequence if it does; how likely and how severe is that consequence; and which safety mechanism handles it. A typical answer names a mechanism from a small, stable family — error-correcting code on a memory, a dual-core lockstep pair, a software test library, a triply-redundant structure with a majority voter.

It is written before your evidence exists Produced by a safety engineer, early, from design data and technology data, and it carries an estimated diagnostic coverage for each mechanism. Fault injection is what converts that estimate into a measurement. If your measurement comes in below the estimate, the architecture's metrics move — and if they move far enough the part misses its target. This is why fault campaigns start late and end badly: they are the last chance to discover that an architectural assumption was optimistic.
Its granularity fixes the shape of your fault list “The FIFO indicates its flags incorrectly, so data is overwritten or lost, and the mechanism is redundant flag logic” tells you exactly where to inject and which signal is the alarm. “The block malfunctions” tells you nothing and cannot be measured. Argue with the granularity while arguing is cheap; you cannot re-cut it in the last four weeks.
Scenario · walk it row by row, on a part you can enumerate The brake controller MCU is small enough to be honest about: a lockstep core pair, its protected memories, a watchdog, and a safety island holding the comparator and the alarm aggregation. The verification lead walks the analysis with the safety engineer before writing any injection infrastructure, and produces one artifact per row: where faults are injected, which signal is the observation point, and which signal is the detection point. On a part this size the walk takes two days and removes almost all the late surprises. On the flagship-A the same walk is a multi-week activity across a dozen sub-teams. The technique does not change with scale; the coordination cost does, and it dominates.

SayThat is why large safety programmes staff a safety architect whose full-time job is keeping the analysis and the campaign definition in agreement.

A HOLISTIC GUIDE19

Chapter 22 · Classification

The deliverable is a classification — and ordinary English gets every one of these words wrong

safeCannot violate the safety goal — either it cannot affect safety-related logic at all, or its effect is one the system tolerates.
single-pointViolates the safety goal and no safety mechanism is present to catch it. This is the class that must be nearly empty.
residualViolates the safety goal in a place where a mechanism is present, but this particular fault is outside what the mechanism covers. The honest measure of how good your mechanism is not.
latentCannot violate the safety goal on its own, and is neither detected by a mechanism nor perceived. It waits, silently, for a second fault to arrive and combine with it. A dead comparator in a lockstep pair is the canonical example — nothing goes wrong until the day the two cores disagree and nobody is listening.
multi-pointA combination that violates the safety goal, classified by whether the mechanism detects it, whether it is merely perceived, or whether it stays latent.

SayLearn these five precisely. “Not detected” is not one of them, and the next two slides are about why.

A HOLISTIC GUIDE20

Chapter 22 · The unit trap

Your campaign counts faults. The metrics are ratios of failure rates.

Your campaign injects a number of faults and reports how many were detected, and the temptation to divide one by the other and call the quotient your diagnostic coverage is overwhelming. It is a unit error.

Each failure mode of each design element carries a base failure rate computed from design data and technology data, and the metric formulas combine those rates — the safe fraction, the residual fraction, the multi-point fractions — into a single number for the element and then for the part. Your campaign's detected fraction is an input applied to a weighted quantity, not the quantity itself.

The practical consequence Two campaigns with identical fault counts can produce different metrics. A fault list that over-samples a large but low-rate structure while under-sampling a small critical one misleads you in a direction no coverage report shows.
So do two things, from the beginning Agree the fault list with the safety engineer per failure mode, and keep the per-mode results separate all the way to the report. A single aggregate percentage across a whole block cannot be composed with anything — which is exactly what makes it useless to the person who has to compute the architectural metric.

SayNothing in the toolflow warns you about this. The tool will happily divide two numbers it has, and the quotient will look like a metric.

A HOLISTIC GUIDE21

Chapter 22 · Fault injection

Good machine, faulty machine — and three words that do not mean here what they meant earlier

Make a second copy of the design with one hypothetical fault inserted — the faulty machine, against the unmodified good machine — and run the same workload on both. At designated strobe times, compare designated signals: if a signal differs between the two runs, the fault has reached it. Two kinds of signal are designated, and confusing them is a common beginner error.

A HOLISTIC GUIDE22

Chapter 22 · Verdicts

A fault that is not detected is not the same as a fault that is not dangerous

Cross the two axes and you get four verdicts. Observed and detected: the mechanism caught it — it corrupted something and the alarm went off. Detected but not observed: the alarm went off without anything being corrupted — not dangerous, if noisy. Neither: it did nothing visible in this run. And observed but not detected — it corrupted the design's output while the mechanism stayed silent. That last class is the dangerous one, and it is the whole point of the campaign.

The distinction that separates a competent safety engineer from a dangerous one A fault never observed in your campaign has two possible explanations, and your campaign cannot tell them apart: either it is genuinely safe — it cannot affect the safety goal under any stimulus — or it is dangerous and your workload simply failed to excite it. Both look identical in the results database. Both are a row that says “not observed”. Which explanation you choose is the largest single lever on your reported metrics: classifying every un-excited fault as safe will get you to any number you like, and an assessor will ask for exactly the argument you did not make.
Structural and formal answer “under any stimulus” A fault outside the cone of influence of every observation point cannot reach one under any workload whatsoever — a property of the netlist, established statically. A fault a proof engine shows can never cause a difference at the observation point is untestable by construction, not merely unstimulated. Real safe faults. Exclude them without apology.
Simulation answers “under this stimulus” A fault your workload did not excite is a fault about which you have learned nothing. It is not evidence of safety; it is absence of evidence, and it must be resolved by better stimulus, by proof, or by a recorded engineering judgment with a name attached.

SayKeep those two apart every time you prune, and the pruning is defensible. Blur them and the campaign is theatre.

A HOLISTIC GUIDE24

Chapter 22 · Verifying the mechanism

A safety mechanism is a design, and it has bugs

It was written by the same people, under the same schedule, from the same specification as the logic it protects. It gets less verification attention than the functional path because it does nothing in the nominal case, and it integrates last because it depends on everything else. A safety mechanism is therefore, structurally, the least-verified block on the part — and the one whose failure the metrics assume away.

1 · Does it fire when it should?the fault campaign — the easiest of the three, answered as a by-product
 →
2 · Does it fire in time?the budgeted interval is part of the requirement
 →
3 · Does it stay silent when nothing is wrong?the question teams forget
Late is not partial credit A mechanism must detect and react within a budgeted interval measured from the moment the fault occurs, and must run continually while the device operates. So a campaign classifies detected-in-time against detected-late, and a late detection is an undetected fault with a misleading log message. The simulation therefore cannot stop at the first difference — set the post-divergence budget from the timing requirement, not from what makes the run finish quickly.
The asymmetry that explains the skip Proving a mechanism fires means injecting a fault — deliberate, scripted, easy to demonstrate. Proving it stays silent means running the design's entire legal operating space with the alarm never asserting: an obligation with no natural stopping point. A mechanism with false positives is a reliability defect, often worse than the fault it guards against, because it takes a healthy system to a safe state — a warning lamp, a limp mode, a dealership visit.

SayThe sensor hub's clock monitor makes the third question concrete. The domain it watches legitimately changes frequency on a low-power transition, legitimately stops during power-down, and legitimately restarts with a ramp — every one of those a healthy event that looks exactly like the failure the monitor exists to catch. The obligation is a cross of every legal power and clock transition against the alarm, with the alarm asserted as an error.

Why the assertion alone proves nothing A wrapper whose error outputs never assert — a design bug tied them off, or a fault killed the mechanism — passes a_no_spurious_ecc_alarm on every run of every test, forever. Silence is exactly what a dead mechanism looks like, and a dead mechanism is the latent fault of the classification. The cover is what makes the silence mean something.
And inject_active is doing real work Without that qualifier the assertion fires on every campaign run, so the team disables it during campaigns, so it protects nothing during exactly the runs where the protected path is most exercised. Gate it on the injection control and it holds in campaign runs too — everywhere the campaign is not currently corrupting something.

SayThe instrument cluster generalises it. The alarm condition must be a proposition that is false exactly when the design is healthy, never a heuristic that happens to correlate with health. When you find yourself verifying a heuristic, the finding belongs back with the architect — early.

A HOLISTIC GUIDE26

Chapter 22 · Verifying the mechanism

The obvious lockstep test passes on a design with a serious defect

Two cores, one comparator. Inject a fault into one core, check the comparator flags a mismatch. It passes — and it establishes almost nothing, because what makes a lockstep pair effective is not that a mismatch is detectable. It is that the two cores fail independently.

What the mechanism actually is On the flagship-A the pair is delayed: the shadow core runs some cycles behind, so a disturbance hitting both at the same instant hits them at different points in their execution and produces a mismatch instead of two identical wrong answers. That delay, and the separation behind it, is the mechanism.
  • Does the delay pipeline preserve the comparison across every stall, flush and interrupt?
  • Do the two cores share any resource — a clock buffer, a reset synchroniser, a power rail, a memory port — whose single failure would corrupt both identically?
  • Does the comparator's own failure get caught by something else? That is the latent-fault question again, and its usual answer is a periodic self-test that provokes a mismatch on purpose and confirms the alarm.
And where the answers come from None of that is found by injecting a fault into one core. It is found by asking what a single physical event could do to both halves at once — the analysis of dependent failures, a discipline of its own that a verification engineer contributes to rather than owns. What you owe it is the list of shared resources your netlist actually contains, which nobody else can produce.

SayNotice the shape repeating from the previous two slides: the interesting obligation is never the one the mechanism was designed to satisfy.

Chapter 23 · The gap

Signed off twice. The second review opens with a question the plan does not contain.

The question What would an attacker want from this block, what are they able to do, and where do those two meet? — and within an hour the room has produced obligations with no rows behind them.

  • Nothing says what becomes of a working key when the key ladder's power domain goes down in the middle of an operation.
  • Nothing says whether the debug port — once opened by the authenticated unlock path everyone trusts — can reach the key ladder, as opposed to merely not being wired to it.
  • And nothing anywhere in the plan names an adversary, which is why none of those questions had a reason to be asked.

Chapter 23 · No anchor

Four consequences, structural rather than a matter of degree

The properties are negative“This key never reaches that bus” is a claim about the complement of the design's intended behaviour. You cannot establish it by demonstrating intended behaviour, however much of it you demonstrate.
Rarity stops being a defenceRisk-driven verification allocates effort by likelihood times cost, and likelihood is computed against a stimulus distribution the team controls. An adversary is not a distribution. An adversary is an optimiser with a budget, who will spend a month arranging exactly the four conditions your generator would only ever have stumbled into — and who, having arranged them once, can arrange them on demand.
The failure is often functionally silentA confidentiality breach need not corrupt any output. In Chapter 3's vocabulary: the bug is activated and it propagates — propagation to an observable point is not the detection mechanism here, it is the failure — but nothing checks, because no checker was ever written for a value that was correct.
Coverage does not closeThere is no enumeration of “everything an attacker might try”, so there is no denominator, so there is no percentage.
And the obvious approaches under-deliver, each in its own way Architecture review is manual and rarely reaches the implementation as built. Red-team exercises are essential for the finished product and find nothing before silicon exists. Formal belongs inside a larger strategy and does not scale to a large design running hardware and software together. Directed tests take substantial effort to write and mostly re-confirm vulnerabilities already known. None is a bad technique — each simply has its strength somewhere other than where an adversary's advantage lies, so a plan built on any one alone inherits precisely its blind spot.

SayThe second row is the one that should unsettle you. Prioritising by unlikeliness is load-bearing for every functional plan in this book, and it is void inside the threat model's scope.

Chapter 23 · What it costs

There is no security-coverage percentage — and the reason is not a tooling shortfall

The output of the process is a threat model, a set of properties discharged against it, a set of properties not discharged with their reasons, and a residual-risk statement someone signs. A chapter that promised a coverage number would be lying.

Why there is no number No enumeration of what an attacker might try ⇒ no denominator ⇒ no percentage. Functional metrics — line, toggle, FSM — correlate only loosely with an attacker's search space, and the field has no settled, tool-friendly definition of security coverage. This is not a temporary tooling shortfall: it is what happens when the space being covered is defined by an opponent rather than by a document.
Which makes the residual a different animal The shape is Chapter 7's sign-off with one difference that matters: the residual is not merely unquantified, it is unquantifiable — because you cannot count what you have not enumerated.
The one thing that transfers — and it is most of the job Everything downstream of the threat model is verification: properties, assumptions, stimulus, coverage, waivers, sign-off. Once someone has written “the working key must not be observable at the debug port under adversary capability C3”, the question of how to establish that is a question this book has spent twenty-two chapters on.

The specialist knowledge is concentrated almost entirely in one artifact. So write that artifact first, and write it as an engineer.

SayThat is uncomfortable, and it is why the discipline leans so hard on structure: if you cannot bound the space, be explicit about which part you looked at, and make each look exhaustive within its scope. Every practice in this chapter follows from that trade.

Chapter 23 · The plan's root

Assets, capabilities, boundaries — and each is useless without the other two

Assets are identified first, because where that is left late the fixes land in the far more expensive post-silicon stage. The obvious ones are cryptographic; the non-obvious ones matter more. The firewall and address-decode configuration that enforces every other protection is an asset: if an adversary can rewrite the enforcement, no other lock needs breaking. And an asset need not be secret — the anti-rollback counter is public by design, and everything depends on nobody being able to decrement it, so what it needs is integrity, not confidentiality.

Capabilities: write capabilities, not attacks — attacks are an open set, capabilities are enumerable, and only an enumerable list can be closed over. Boundaries are the surfaces where the tier changes, and they make the first two lists checkable: a property is always “asset A does not cross boundary B under capability C”.

C1Unprivileged software on the host cluster: loads and stores, programming what it is allowed to program, and timing itself.
C2Privileged software: everything in C1, plus configuration of the interconnect, the MMU, the power controller and the debug fabric.
C3Physical access to the package pins: probing debug, measuring supply current and emission, perturbing clock and supply.
C4Invasive physical access, to decapsulation and direct die probing. Declared out of scope — with the reason written down.

SayThe reason for the C4 exclusion: countering it is a packaging, sensor and countermeasure-design problem whose evidence does not come from RTL verification, and pretending otherwise would put rows in a plan that no pre-silicon activity could ever discharge. An out-of-scope declaration with a reason is engineering. An out-of-scope declaration without one is where the next escape lives.

Chapter 23 · The properties

Confidentiality quantifies over pairs of executions. That is a mismatch of shape.

Both shapes are statements about flow

Integrity is violated when an unauthorised agent — software or physical — can modify the state of a target register or memory: untrusted sources must not flow to trusted state. Confidentiality is violated when an unauthorised agent can read it: secret sources must not flow to observable destinations. Every row of the table is one or the other — which is why sorting assets by which they need was worth the effort.

Now compare a functional property

Chapter 11's 4 KB-boundary property is a claim about values at a point: given an accepted incrementing write address, this arithmetic relation holds. It is decidable by looking at one execution at that point. A confidentiality property is not decidable that way at all: its natural statement is change the secret and nothing the adversary can see may change — and a concurrent assertion evaluates sampled values from one execution.

You cannot write around this with a cleverer sequence It is a mismatch of shape rather than a limitation of expressiveness — and it is exactly why information-flow analysis exists as a separate technique rather than as a style of assertion.

SayHold that thought for two slides. Everything expressible as a single-execution invariant goes to formal; everything that is really a statement about dependence goes somewhere else.

Chapter 23 · Information flow

Four parts to a rule — and the exception clause carries the whole argument

Labels are attached to data — secret or public, trusted or untrusted — and their propagation is followed through the design. The label is usually called taint, and the mental model is worth stating exactly: you are not tracking the value, you are tracking dependence. Anything whose value could differ because the secret differs is tainted — whether it holds a copy of the secret, a function of it, or merely a bit that was set because of it.

PartWhat it namesOn the crypto engine
Source setthe asset, as the signals that hold itevery bit of the key ladder's working-key output

Read the fourth row again — it is worse than an over-constraining assumption, in one specific way In words the rule is: the working key must not flow to any output, ignoring the cipher's ciphertext output. Without the exception the rule fails immediately and correctly — the ciphertext depends on the key; that is what a cipher is. With it, the rule becomes checkable and exactly as strong as the exception is narrow. And an over-constraining assumption looks like a modelling shortcut, so a reviewer who reads assumption lists will challenge it — whereas an exception clause looks like domain knowledge, so it reads as competence rather than as a concession and gets waved through. Widen it by one signal and you have declared a whole port secure.

Say“The ciphertext output is declassified because the cipher is trusted” is an argument. “We added busy to the ignore list because the rule kept failing” is a defect with a comment on it. Every exception is a row, with a written argument, an owner and an expiry — reviewed exactly like a waiver.

A HOLISTIC GUIDE38

Chapter 23 · Information flow

A no-connection result proves non-adjacency. The key's own path is supposed to be there.

What connectivity established

Chapter 15 proved the negative rows for this exact key ladder — no structural path to a bus-readable address, to the debug data register, or to a scan-observable point. That is a structural result: no path exists.

What it cannot establish

The key bus from the ladder to the cipher core is a path that exists by design. Nobody is going to prove it away. The question is whether anything reachable downstream depends on the key other than through the cipher's intended transformation — and no cone-of-influence check can answer it, because the cone is supposed to be there.

Which is precisely the failure in the opening result Structurally, key and datapath are adjacent — they must be. Functionally, a value carrying the key survived to the output pin. A team holding a green connectivity report and calling it non-leakage has proved non-adjacency and filed it under the wrong heading.
Scenario · the GPU, where the failure is never a wire Four shader clusters share a unified memory and contexts belonging to different applications time-slice it. Asset: one context's data. Sink: anything the next context can read. Boundary: the context switch. The failure is residue — state a functional test cannot see because the next context overwrites it before reading, and that a taint rule sees immediately because it tracks dependence rather than values. And note what makes the rule statable at all: the activation condition. Without it the rule is “context A's data never reaches memory”, which is false by construction, since writing to memory is the point.

SayThe interesting covers are on the sources, not the sinks: did this run ever put a secret in the source register, ever switch context with live data resident, ever load a key at all. A flow rule evaluated over a run in which no source was ever tainted is a vacuous pass wearing a different hat — green report, nothing tracked. And scope one rule per threat-model row, so every alert arrives already attached to an asset, a capability and a boundary: a screen returning four hundred benign alerts will be ignored within two weeks, and the instinct to loosen the policy is the move that starts deleting real findings.

A HOLISTIC GUIDE39

Chapter 23 · Side channels

Sort the channels by whether the leaking quantity exists in your model

An RTL model represents logic values at clock ticks and nothing else. It does not model supply current badly, or approximately. It does not model supply current at all.

inside the model
Timing
the good news		A cycle count is a signal-level fact: if the number of cycles between an operation's start and its completion depends on key material, that dependence is present in the RTL. Where the specification declares a fixed latency, the claim is single-execution and mechanical: $rose(op_start) |-> ##LAT op_done, with a cover on op_start. Where the latency legitimately varies, that assertion is false and the claim becomes a flow rule instead: no key bit may flow to the completion signal. op_done is just another sink. A timing channel is not a new category of problem; it is a confidentiality property whose sink happens to be a control signal rather than a data bus.
outside the model
Power and emission
the bad news		Nothing in the RTL holds them. Pre-silicon work can only reason over proxies — switching activity, performance counters, timing distributions. Be precise about what a proxy licenses: switching activity correlates with dynamic power; it is not power, and a countermeasure that improves the proxy has been shown to improve the proxy. Ranking structures by risk and comparing a countermeasure against its absence are real value. A leakage verdict is not available at this abstraction, and a report that implies one is worse than none, because it retires a question that is not closed.

SayAnd the capability tier is itself a design decision. Physical side channels are nominally C3 — they need the package. But software-controllable voltage and frequency scaling, and power monitoring, are ordinary features of modern chipsets, and they let an attacker mount fault-injection and side-channel attacks without physical access. The flagship has three operating points, and something selects among them: if that selector is reachable from C1 or C2, a whole row's capability tier has quietly changed, and every property justified by “the adversary would need physical access” is now unsupported. That is the question a verification engineer is placed to ask — not how a power analysis works, but which side of a boundary that selector's enable sits on.

TM-06fails — its subject is a physical quantity with no representation in the model. No signal list exists, and nothing will ever settle it. Between those poles sit the properties whose signals exist but whose exception is doing suspicious work, and that is where a reviewer should spend the meeting.
What TM-06 gets instead of a proof A named countermeasure recorded in the design review; a proxy comparison showing it moves the proxy in the expected direction, with its own limitations written down; and a post-silicon leakage assessment on the plan with a date and an owner. Chapter 7's conditional sign-off, applied honestly. What it is not is a green tick — and that distinction is the single most useful thing to hold clearly in a security review.

SayWhich is also the answer to what someone without a security background contributes. Not attacks, and not cryptography: three questions asked persistently — who can write this register?, what happens to this state across this transition?, what exactly does this exception permit? None requires knowing how a power analysis works. And a security campaign is a campaign in Chapter 12's exact sense: it must compete for emulator slots explicitly, with a named block list and a named window, because an activity described as ongoing background work will lose every scheduling argument it is never present for.

Part VI · The cross-chapter lesson

Three domains, three incompatible answers to one question — what counts as evidence?

The sharpest contrast in Part VI is between the middle column and the right one Chapter 22 is entirely about percentages against thresholds — tabulated, per level, agreed before the campaign runs. Chapter 23 says there is no percentage, there will not be one soon, and that is not a tooling shortfall: it is what happens when the space being covered is defined by an opponent rather than by a document. Carry the two habits into the same review and one of them will corrupt the other — either a security report grows a number nobody can defend, or a safety residue gets waved through as unquantifiable when it is nothing of the kind.

SayNo single chapter states this, and it is the real lesson of Part VI: before you can say whether the evidence is enough, you have to say what kind of thing the evidence is. Get that wrong and every downstream argument inherits the error. Note too that all three end at a name, but at different names — the analog engineer correlates the model while the verification team owns its register row and its expiry; the safety engineer owns the residual risk while the verification lead owns the accuracy of the statement; and the security residual takes one signature on a quantity nobody can count.

Part VI · Closing

The through-line: a market you did not choose decides what counts as done

Chapter 21's market is physics — the digital abstraction stops and the oracle is rebuilt as a band. Chapter 22's is a standard and its assessor — the argument stops living in the room and becomes the deliverable. Chapter 23's is an opponent — the scope stops coming from the specification. None of the three is optional once you are inside it, and none of them accepts the others' evidence.

21Mixed-signal — the band, its reference point, and the model register behind both
22Safety — classify, weigh by failure rate, and argue the residue
23Security — named claims, named gaps, and no percentage
What Part VI deliberately left open The analog block itself — its performance, noise, linearity and corner behaviour belong to the analog team, who have tools and instincts you do not. The standards' own texts, which should be read rather than paraphrased. Cryptanalysis, and how a power analysis actually works. And the manufacturing-test flow the fault models were borrowed from.
Eight sentences worth leaving with
  • A debugging convenience becomes the specification the moment nobody writes down where the number came from.
  • A band is only as meaningful as the thing it is a percentage of.
  • An analog model is an assumption with a waveform.
  • Faults are counted; metrics are weighted by failure rates.
  • “Not detected” and “not dangerous” are different verdicts, and only one of them is yours to declare.
  • A safety mechanism is the least-verified block on the part and the one the metrics assume works.
  • A no-connection result proves non-adjacency; only a flow argument speaks to the paths that exist by design.
  • A threat model in which every row closes was written backwards from the tools you own.
