Static Verification

Exhaustive over structure, silent about function — and a setup file where all the engineering actually lives.

A HOLISTIC GUIDE4

Chapter 13 · The opening scenario

One board in forty hangs on wake-up. The regression is green.

The event unit encodes the wake reason in a three-bit cause code, produced on the 32 kHz always-on clock and consumed at 200 MHz. Sparse encoding — four legal codes across eight code points — each bit crossing through its own two-flop synchronizer. Three textbook synchronizers, and the linter has nothing to say about any of them.

What the board doesThe code changes from 3'b010 (GPIO wake) to 3'b100 (comparator wake), so two bits change at once and each destination flop resolves independently. For one system cycle the destination observes 3'b110 — a reserved code the source never produced. The decoder has a branch for each legal cause and none for the rest, so it holds its previous decode; the wake sequencer latches the stale value and the handshake never completes.
Why simulation could not have shown itThe source flops change at one instant of simulated time, the destination samples one instant later, and what it samples is exactly what the source drove. Metastability is a behaviour of a flip-flop with real timing, not of RTL. Eleven thousand seeds, every wake path the plan enumerated, the scoreboard silent throughout — the design is correct at the level the simulation can see.

The lab is no better: demonstrating this class needs a gate-level model with timing that does not exist yet at RTL sign-off, and the bugs are hard to reproduce once silicon arrives.

What would have found it, in seconds, before a testbench existedA structural analysis that walks the elaborated design, finds every path leaving one clock domain and entering another, and asks whether a multi-bit crossing is protected against its bits resolving independently. No stimulus, no reference model, no seed.

SayAsk the room how many of their CDC reports were last read by someone still on the project.

Chapter 13 · The entry gate

No stimulus, no expected output — and no opinion about function

It analyses the design description itself. Chapter 3's two limits do not apply, because it has neither power: it drives nothing, so nothing is unreachable and no coverage question arises; it observes nothing, so nothing it reports is about what the design computes.

Which is what earns it the front of the flowIt runs the first day RTL compiles, and it is deterministic — no seed, an identical report on unchanged source. That is what makes it usable as a per-commit gate, and as a sign-off row with its own audited waiver file.
And the boundary, stated exactlyIt finds problems deducible from code structure, never problems in the algorithm. A spell checker finds a misspelled word and will never notice you wrote with where you meant width.

The setup is the hard part

A structural CDC check is a setup followed by a button. Somebody must declare which clocks are asynchronous to which, which inputs are constant in this mode, which signals are pseudo-static, which buses are gray-coded.

Do not point it at the timing constraintsA false path in timing means do not schedule this. A false path in CDC means there is no crossing here at all — a much stronger claim, and usually a wrong one.

“Three clocks” is not “three clock domains”. Had the 50 MHz peripheral clock been the system clock divided by four, the APB boundary would carry no crossing at all. It has its own source, so it does. Nothing in the RTL distinguishes the two cases.
PER-COMMIT GATEElaboration with the production parameters · lint at must-fix severity only · structural CDC and RDC against a checked-in setup file · nothing else
OUTSIDE ITProtocol assertions and metastability injection nightly · the formal X-propagation proof as a scoped campaign — never a gate

It decays through the setup, not the checks: six months on, “the CDC report is clean” means clean under assumptions last examined by someone who has left the project.

Chapter 13 · Lint

From noise to policy — and a report several levels below the bug

module wake_decode (
  input  logic [2:0] cause,
  output logic [1:0] branch
);
  always_comb begin
    case (cause)          // sparse, no default
      3'd0 : branch = 2'd0;  // no wake pending
      3'd1 : branch = 2'd1;  // timer
      3'd2 : branch = 2'd2;  // GPIO
      3'd4 : branch = 2'd3;  // comparator
    endcase
  end
endmodule
What the linter sees — and what it does notFour of eight values are decoded; for the rest no assignment executes, so branch keeps what it held. The report reads synthesis-intent mismatch, missing default. It does not know that cause crosses a clock boundary, or that 3'd6 is the transient the lab is hitting. Structural, correct, and several levels of abstraction below the bug.

Four families: synthesis-intent mismatches — the language itself asks tools to flag an always_comb that can infer a latch; width and type errors; connectivity; and constructs whose semantics differ from what the author meant. casex treats x and z as don't-care in the items or the expression, so a runtime unknown on the selector takes a branch nobody chose.

Why teams drown — and it is not a tool defectLint errs on the side of caution, so engineers who chase non-existent problems for a week stop reading the output. Two multipliers: replication — four shader clusters report one shared construct once per instance, so 11,000 findings may be forty distinct constructs — and inherited code, which is somebody else's signal, not noise.
Three disciplines, and only the first is about the toolClassify by severity before the first run — block / waivable by a named owner / informational. Filter the output; never disable the check, and let naming conventions carry the filter so it is mechanical. Lint as the code is written, while its author still holds the context.

On an inherited block, do not attempt closure: baseline the report and gate on the delta. Retire rule classes with a failure mode behind them — never instance counts, which measure elaboration depth.

The one thing this book's corpus lets a lint section cite — and it is a warning, not a result. On a Broadcom power-management controller, lint had been run and its errors and warnings waived by the designer; the bug that mattered was found afterwards, by formal. No source reports a lint deployment, a rule-set decision or a measured lint result, so the disciplines above are method, not evidence. (DVCon, p.6.)

A HOLISTIC GUIDE7

Chapter 13 · Clock-domain crossing

Metastability cannot be removed — only given time to decay

Mean time between failures — read the shape, not the numbers

MTBF = e(Ts/Tc) / (Tw · Fc · Fd)

Two terms sit in the exponent — the settling window Ts, and the flop's time constant Tc as its divisor. Only Tw, Fc and Fd are linear.

So the first exponential lever is the gap between the first flop settling and the second sampling it — why two flops work at all, and why anything eroding it (a slow route, a scan multiplexer, clock skew) hurts out of all proportion to its size.

What it does not sayNothing about how often a metastable condition occurs — those are frequent. A design does not fail because metastability happened. It fails because settling did not finish in the window available, or because there was no synchronizer at all.
StructureIts precondition
Two-flop
one async bit		No combinational logic on the path; no pulse too narrow to sample; data stable across more than two destination edges
Gray parallel
one sync per bit		Exactly one bit changes at a time — so at most one bit goes metastable, resolving to the old code or the new one
Handshake
multi-bit, any code		Data is not synchronized at all: only request and acknowledge are, and the bus is held stable until the acknowledge returns
Async FIFO
streaming		Gray pointers both ways, payload through dual-ported memory. Buys bandwidth, and throttling

The opening scenario, stated as a ruleFixing metastability and fixing data coherency are independent problems. For one bit the coin can land either way and both faces are legal; for several bits you need all the coins to land the same way — so the answer is a gray code, a handshake or a FIFO, never three correct synchronizers. Had anyone declared that cause bus gray-coded, the structural check would have accepted one synchronizer per bit and reported nothing.

Chapter 13 · Structural checks and protocol checks

A clean structural report is half of CDC verification

The structural check asks whether a recognised synchronizer stands where one is required. It does not analyse functionality, so a valid structure passes. The other half — that structure's preconditions — is an assertion problem.

// Wrong: samples the crossing signal on the
// clock that cannot see the problem.
property p_min_pulse_wrong;
  @(posedge dst_clk) $changed(src_sig)
    |=> $stable(src_sig)[*2];
endproperty
The flaw is in the noticingA source pulse narrower than a destination period falls entirely between two destination edges. $changed is then never true, the antecedent never fires, and the property passes having checked nothing — a clean run reported for exactly the crossing it was written to protect. Only a cover on its antecedent would have exposed it.
 
// Right: sampled fast enough to see a pulse
// the destination could miss.
//   N = ceil( 2 * dst period / fast period )
module cdc_pulse_chk #(parameter int N = 2) (
  input logic fast_clk, rst_n, src_sig
);
  property p_min_pulse;
    @(posedge fast_clk) disable iff (!rst_n)
    $changed(src_sig) |=> $stable(src_sig)[*N];
  endproperty
  a_min_pulse : assert property (p_min_pulse);
endmodule
Compute N, and the property prices the designFor the downward crossing — 200 MHz fast clock, 32 kHz destination — N is 12,500. The number states in one figure the cost the level-pulse design was hiding, which is why the answer in that direction is a handshake.

And the shape that survives review, because each crossing is individually correctReconvergence. Two peripheral-domain flags, each properly synchronized, feeding fifo_empty && xfer_done in the system domain. The synchronizers resolve independently, so the conjunction can assert for a cycle when the source never had both true — or be missed when it did. The cure is architectural: qualify one signal with the other, or carry both across a single handshake.

A HOLISTIC GUIDE9

Chapter 13 · Reset-domain crossing

Same clock, different reset: a discipline of its own

An asynchronously reset flop has a third timing requirement beside setup and hold: recovery time, between reset release and the next clock edge. It splits in two, and only the second is what the industry means by RDC.

DE-ASSERTION  Release lands inside some flop's recovery window sooner or later. Cure: the reset synchronizer — assert asynchronously, release synchronously. Purely structural, so static analysis is sufficient.

ASSERTION — RDC  A register cleared asynchronously changes at a moment unrelated to any clock edge, and a register in a different reset domain, and so not being reset, samples it.

Why this is not a footnote to CDCThe domains in question are reset domains. Both registers can share a clock, so a design with exactly one clock — and not one clock-domain crossing in it — can be full of reset-domain crossings, and a clean CDC report says nothing about them.
Scenario — the sensor hub's always-on islandEntirely on the 32 kHz clock, with two resets: a power-on reset, and a soft reset firmware pulses to restart the fusion pipeline. Its CDC report is empty — one clock, no crossings. In the lab, reconfiguring a sensor occasionally produces a spurious wake interrupt.

Declare the two resets as separate domains and every path into the wake decision is reported. sample_valid clears at an instant unrelated to the clock edge; the wake-decision register, in the other reset domain and still clocking, samples exactly then. Neither register is wrong; both resets are correct.
Fix 1 · order the assertionsIf the destination reset is already asserted it samples nothing — which is why the standard carries a reset assertion sequence and a reset group.
Fix 2 · qualify the pathBlock the crossing while the source reset is active. Load-bearing: the qualifier must itself be synchronous with the destination.
Fix 3 · synchronize the resetThe crossing becomes an ordinary synchronous path. Cheapest of the three here: the island's clock never stops.

Accellera's CDC Working Group — 154 members from 24 companies, Arm, AMD, Apple, Google, IBM, Infineon, Intel, NVIDIA, Qualcomm, Samsung and ST among them — released v0.1 covering CDC alone in October 2023; RDC entered scope at the very next release, v0.3, nine months later. A participation fact, not a results fact: it says the industry found this hard enough to standardise, not that the tools work. (Accellera CDC/RDC IP Abstraction Standard v1.0; DVCon US 2026 tutorial, slide 58.)

A HOLISTIC GUIDE10

Chapter 13 · X-propagation

RTL simulation lies optimistically and pessimistically at once

A four-valued model driving a two-valued device is lossy in both directions, so a simulation can pass a test silicon fails and fail a test silicon passes. Which is why the answer is never “make the simulator pessimistic everywhere” — asynchronous reset works because of X-optimism.

X-optimism — the language's semantics, not a simulator defectAn if takes the true branch only for a nonzero known value; the false branch is taken for 0, x and z alike. So a condition nobody can predict produces a decision nobody chose, and the run continues as though it were deliberate. case and the edge constructs behave the same way.
X-pessimism — the opposite error, and the visible oneWith a unknown, both a & ~a and a | ~a evaluate to x where silicon gives a definite 0 and 1. Arithmetic is all-or-nothing: 3'b000 + 3'b01x is 3'bxxx.
Scenario — the crypto engine's unreset key-valid flagThe negative test that matters most, “no ciphertext before a key is loaded”, passes on every seed. The flag powers up unknown, so if (key_valid) takes the else branch and the engine refuses to encrypt: the test passes because of X-optimism, not because of the design. In silicon the flop powers up definite, and on some corners it is one.

The cure is not a better test but a reset — and in general, attack the sources rather than the propagation. A 2014 case study is the shape: an audio block taken from sixteen channels to seventeen, an index one past the end, and a state machine that X-optimism sent back to idle under a fully passing regression.
Answer 1 · gate levelOptimism largely goes — but pessimism becomes more prevalent, and the unknowns are cleared by depositing known values, iteration after iteration. Arrives late, covers little.
Answer 2 · a simulator's X-modeMerges the 0 and 1 results at each decision, converting optimism into an honest unknown. Costs performance, so in practice a named regression variant rather than a default.
Answer 3 · formal X-propagationRun blindly it hits the capacity wall: a whole IP on a two-hour budget returned bounded proofs and no violations on a design known to contain an X-optimism bug. Not a wrong answer — an empty one.

Broadcom quad-core application processor: a power-management controller that had passed extensive block-level UVM constrained-random simulation, SoC-level directed tests and a waived lint run still held an unreset flip-flop whose first-cycle X was masked by RTL X-optimism. Formal reset analysis found four such flip-flops; the X-prop app traced every assertion failure to one — pre-tape-out (DVCon, pp.6-7).

Chapter 14 · The opening scenario

Six weeks of green nights. One number should have stopped the review.

The bound protocol checker from Chapter 11 sits on all nine crossbar ports; its assertions have never fired; the block is a week from sign-off. On the four subordinate-side instances the cover c_w_overlap — a second write address accepted at a subordinate while an earlier burst is still unfinished on the write-data channel — reads zero. Chapter 11 named that cover as the precondition of exactly one hazard, and in six weeks no test produced it.

Same file, same properties, different engineAn engineer points a proof engine at one subordinate port instead of a simulator. Overnight it returns a counterexample eleven cycles long: two managers have writes in flight to the same subordinate, the subordinate back-pressures the write-data channel, and the crossbar interleaves their beats into one stream. Beats from two bursts are counted as one, and the count no longer matches the length the address at the head of the queue promised.
Nothing about the property changed. The question did.A simulator asks did any run I performed break this rule? A proof engine asks can anything break this rule? — and on blocks of the right size the second question is answerable in a night.

The same run returned three other things: two properties proven, one undetermined, and one proven only because an assumption nobody had reviewed forbade the very traffic that would have broken it. Those four results are the chapter. The last is the one that will hurt you.

SaySix weeks of green is not evidence of anything until you know which covers were empty while it ran.

A HOLISTIC GUIDE13

Chapter 14 · What a proof is, and what it is over

Four outcomes, not two — and three qualifiers on every one of them

Strip the tool away and a synchronous design is a finite transition system. Model checking computes the reachable states by fixed-point analysis and checks the property against that set — an exhaustive search which, because the state space is finite, is guaranteed to terminate.

PROVENNo reachable state and no legal input sequence violates it — subject to the three qualifiers opposite
FALSIFIEDA counterexample: the input sequence leading to the failure, with no irrelevant history attached
BOUNDEDNo violation up to n cycles — a statement about the near future only
UNDETERMINEDThe tool gave up: timeout, memory, or an incomplete algorithm

A cover behaves symmetrically. Hit: a witness. Not hit: unreachable under the specified assumptions — or it ran out of memory, a third answer wearing the second one's clothes.
The modelThe RTL as elaborated, not silicon. Nothing about the netlist, timing or firmware — and nothing about what you did not model: blackbox a submodule and the proof is over the replacement.
The assumptionsIf the real environment violates them the device may fail despite successful verification. The redeeming feature, and it is real: formal forces them to be written down.
The depthIf the result is bounded, the property is guaranteed only within the bound.

An empty cover in simulation means “no test did this”. Unreachable in formal means “nothing can do this”. Only the second is a statement about the design.

Which is why “the crossbar has been formally verified” is not a claim at allThe useful form is longer and duller: these five properties, on this RTL revision, under these five assumptions, proven unbounded except one which holds to depth 78. That sentence is auditable. The short one is a mood.

Now apply the three qualifiers, because they turn a green tick into a sentence you can defend at a review.

ModelThe midend legalizer and the AXI backend as elaborated. It contains the splitting arithmetic where the canonical bug lives — and it does not contain the register frontend, if you blackboxed it.
AssumptionsWhatever you said about how descriptors arrive. Assume a positive stride and you have deleted the negative-stride bug from the model rather than proved it absent.
DepthIf bounded, long enough for a descriptor to be programmed, legalized, split and emitted. A bound that never reaches the first accepted address proves the property over a stretch of silence.
A HOLISTIC GUIDE15

Chapter 14 · Properties and assumptions

Green is the dangerous colour

Assertions and constraints are one artifact with three hats — a generator in Chapter 9, an assertion in Chapter 11, an assumption here. The hats are not interchangeable. In simulation an assume is checked exactly like an assertion. In formal it is never checked: it deletes traces, and the assertions are proved over what survives.

A missing assumption announces itselfThe model does things the real environment never would, so the engine finds a violation that cannot happen — a spurious counterexample. Irritating, costs you an afternoon, and it arrives in red.
An extra assumption announces nothingThere is nothing to look at. The report is simply greener than before. That asymmetry is why a sign-off review reads the assume list, not the checkmark list.

The loud grade — the empty model. Two assumptions that contradict each other, or one that contradicts the design's own behaviour. Intuition says every assertion should fail; the opposite happens and all of them pass vacuously, because the proof's hypothesis is that all assumptions hold, and that hypothesis is itself false. Cheap prophylactic, applicable by eye: every assumption should have a design input or a free variable in its support.

The quiet grade — the satisfiable narrowing. This is the one that reaches sign-off. Assumptions consistent, model far from empty, most properties still proving for the right reasons — and one clause has removed the exact traffic the interesting property was written for.

And formal makes it worse in one specific wayIn simulation, deleting a scenario shows up as a coverage hole, because coverage is measured on what ran. In formal there is no stimulus to measure, so the deletion leaves no trace anywhere but in the assumption text. Over-constraining is usually not obvious and cannot always be found by automatic tools — which is why validating the assumptions is a task in its own right.

Chapter 14 · Worked example — the crypto engine

The property was not so much proved as evacuated

The inline AES-GCM engine on the memory path carries Chapter 11's two properties: a key may not be loaded while an operation is in flight, and ciphertext may not be presented under an unauthenticated key. Neither proof converges — the key ladder plus the GCM datapath is too much state — so an engineer encodes what the specification's boot sequence says.

m_auth_before_load : assume property (
  @(posedge clk) disable iff (!rst_n)
  $rose(key_load) |-> auth_done);

Both properties now prove in minutes.

The discipline: delete the assumption and re-run before believing either resultThis one does not merely shrink the model. It deletes the entire class of traces in which key material enters the engine unauthenticated — the class a_no_ct_unauth exists to catch.
In a functional proofAn assumption is a promise about a cooperative neighbour, and the worst case is a buggy neighbour.
In a security proofThe environment is an adversary who has read your assumption list. Every assumption is a concession, and each one owes an answer to why can the attacker not do this? Here there is none: an attacker able to drive key_load is the threat.
Where the obligation actually belongedOn the boot ROM's proof, to be discharged — not on the engine's, to be enjoyed. Chapter 16 moves it there in three steps, all of them bookkeeping.

SayThe tell is in the timing: a property that would not converge for days proves in seconds shortly after an assumption is added.

A HOLISTIC GUIDE17

Chapter 14 · Discharging assumptions instead of trusting them

One file, two directives, and a record of which side you stood on

module xbar_port_checker #(
  parameter bit ASSUME_MODE = 1'b0,  // 1 = constrain, 0 = check
  parameter int unsigned IDW = 4, AW = 32
) (
  input logic           clk, rst_n, awvalid, awready,
  input logic [IDW-1:0] awid,
  input logic [AW-1:0]  awaddr,
  input logic [7:0]     awlen,
  input logic [2:0]     awsize,
  input logic [1:0]     awburst
);
  property p_aw_stable;
    @(posedge clk) disable iff (!rst_n)
    (awvalid && !awready) |=> awvalid &&
      $stable({awid, awaddr, awlen, awsize, awburst});
  endproperty

  if (ASSUME_MODE) begin : g_env
    m_aw_stable : assume property (p_aw_stable);
  end else begin : g_dut
    a_aw_stable : assert property (p_aw_stable);
  end
endmodule

Because an assertion in one verification is a constraint in another, an assumption on a block's inputs should be proven as an assertion on whatever drives them. That is assume-guarantee: properties of a system deduced from properties of its components, without ever model-checking the complete model — the thing that will not converge.

The parameter is not decorationIt records which side of the boundary you were standing on, and makes “who guarantees this?” a question with a location rather than an opinion.
One thing has to change first, and it is not a propertyChapter 11's interface model holds each accepted address in an unbounded queue — which a simulator is happy with and a proof engine cannot encode, because termination was guaranteed by the state space being finite. Cap it at the port's outstanding-write capacity: a fact about the crossbar, proven on its own and handed back as a lemma.

Cannot discharge it? Then check it in simulation — and again in simulation of the larger model the block integrates into. An assumption that is nowhere checked, in any engine, is a comment.

Which gives the artifact this section argues for: an assumption register, reviewed like a waiver list. One row per assumption, four columns — the text, who owns the behaviour it describes, how it is discharged, and what breaks if it is wrong.

A HOLISTIC GUIDE18

Chapter 14 · Bounded and unbounded proof

Two engines behind almost every green line you will read

Bounded model checking — unrolling

For each cycle of an interval of length k it makes a fresh copy of the combinational logic, each copy feeding the next, until the whole finite-time behaviour is one combinational circuit. That circuit and the negation of the property go to a satisfiability solver. The one-line intuition: equivalent to an exhaustive simulation with the same bound on the number of cycles.

So a bounded run's success is not a proofIt says the property cannot be violated too soon — and the initial state need not be the reset state. Good tools report “the assertion has not been violated up to bound 50 clock cycles” rather than “the assertion passed”. Do not paraphrase that into your own report.

Push past the sequential depth — the longest shortest-path from an initial state to any reachable state — and a bounded result is a proof of a safety property. That is usually not available: the solver's cost grows, and computing the sequential depth is itself hard.

Induction — unrolling from an arbitrary state

Stop fixing the starting state: unroll from any state characterised by a predicate P. If every reset state satisfies P, and every interval starting in P both upholds the property and ends in P, the property holds for arbitrarily long time frames — good forever, from a computation no longer than a bounded one. The first condition is the one left out of the telling, and it is what keeps the argument from being empty: P = false is closed under transitions too.

The price is a new failure mode, and it eats weeksIf P over-approximates the reachable state space, the engine starts intervals in states the design can never occupy and produces spurious counterexamples from them. The remedy is a strengthened invariant: additional assertions that rule those starting states out.
In practice this is a readable skill, not a theoretical oneWhen a counterexample arrives, look at cycle zero first and ask whether the design could be there at all. A FIFO whose occupancy reads 7 while its two pointers are equal. A one-hot state vector with two bits set. An outstanding count of 3 on a port that holds at most 2. Each observation becomes a helper assertion — proven on its own, then supplied to the engine as an invariant.
A HOLISTIC GUIDE19

Chapter 14 · Reading a depth number

Same block, same run, same number — two different amounts of evidence

The rule of thumb — a bound a little larger than the pipeline depth — misleads, because most interesting properties are not pipeline-shaped. Do the count. One run on the DMA backend, bounded at 40 cycles, two of Chapter 11's properties on it:

a_no_overflow — 40 is a generous boundIt guards a datapath FIFO of 16 entries. Filling it takes at least sixteen pushes with no intervening pop, so the interesting state is reachable well inside forty cycles — and the paired c_full cover confirms it with a witness.
a_w_burst_len — 40 is a stretch of silenceIt reconciles a burst's beat count against the length its address promised, and can only do so at WLAST. Maximum burst is 256 beats, so that WLAST cannot arrive until the 256th data beat has been handshaken. Inside forty cycles no burst longer than about forty beats completes at all: proven for short bursts, completely silent about long ones.

And one cycle either side of a bound can be the whole resultThis chapter's opening counterexample is eleven cycles long. A run stopped at ten would have reported not violated up to 10 cycles — green, filed, and wrong.

Hence a discipline that costs one extra directive per propertyBefore trusting a bounded pass, run the property's antecedent — or the interesting state it guards — as a cover under the same bound. A cover landing below the bound validates it; a cover with no witness inside means the proof is a statement about a stretch of silence.

A HOLISTIC GUIDE20

Chapter 14 · Abstraction: what you throw away

Not an advanced topic. The technique — with a knife edge.

For a proof to complete, the model must be small enough to finish in the CPU and memory available. Every reduction changes the set of behaviours the model can exhibit, and the direction of that change decides which results you may still believe.

Over-approximation — adds behavioursThe abstract model allows more traces, so a proof on it holds on the original: over-approximation is sound, and a success is always accurate. A failure may be spurious.
Under-approximation — removes behavioursA failure is always real, so it is safe. But a pass means nothing — exactly why such tools say “not violated up to bound 50”.

The practical hazard is human, not logical. Someone who has waded through twenty impossible traces starts skimming. The twenty-first is real — the capacity a reduction buys is paid for in the analysis of spurious failures.

A HOLISTIC GUIDE21

Chapter 14 · The canonical proof abstraction

Two caches, one address — and the list you write at the moment of the cut

The coherent hub is the standard teaching case because its state space is a product of things you cannot bound: the state of every line, in every cache, for every address. Chapter 11 left one invariant with an explicit promise — at most one cache may hold a line Modified:

a_single_writer : assert property (
  @(posedge clk) disable iff (!rst_n)
  $onehot0(modified_vec));
What survives a cut to two caches and one addressThe directory's transition rules for a line, every race between two requesters for it, the ordering of invalidations against data responses, and — since livelock lives on a single contended line — starvation of one requester by the other. None of it is reachable by simulation at any run length you can afford.
What does not survive — write it down now, nobody reconstructs it in three monthsA second address: the classic coherence deadlock — two agents acquiring two lines in opposite orders — is invisible by construction. Capacity: with one address there are no conflict evictions. A third sharer, including the sharer-vector encoding and its overflow.
And a warning about the cut itselfCutting many caches down to two is not a sound abstraction in the sense opposite: freeing and setting have a defined direction of error, and deleting requesters has none. It rests on a symmetry argument — that the hub treats its requesters interchangeably — which is a claim about the RTL, not a theorem. If the directory arbitrates fixed-priority by requester index it is simply false.

The general answer to “how do I avoid throwing away the bug”You cannot, entirely — an abstraction that kept everything would not converge. What you can do is name the bug classes it deletes, at the time you delete them, and give each one somewhere else to be caught: the two-line deadlock to a separate proof, the eviction path to system-level simulation with a cache-thrashing profile, the sharer-vector overflow to a directed test. Each becomes a plan row reading not covered by proof P-COH-2 — covered by… A proof whose deletions are enumerated is evidence; a proof whose deletions are implicit is a slogan.

A HOLISTIC GUIDE22

Chapter 14 · Convergence: the undetermined property

A cheapest-first order — not the order the menu is written in

Sooner or later a run comes back neither green nor red. Getting a conclusive answer means refining the verification model, and the order you work through the options is what separates an afternoon from a fortnight.

1Ask whether the property is even true. Run bounded, run deep. An undetermined property is sometimes a false one whose counterexample sits further out than the last bound you tried — one overnight job instead of a week of strengthening.
2Ask whether it was written for this engine. In simulation an inefficient assertion costs runtime; in formal it can be fatal. Where one text must serve both engines, the formal-efficient form should win.
3Split it. A property asserting five things at once is five proofs sharing one worst case. Separated, the report names the one that did not close instead of hiding four successes behind it.
4Prove lemmas and feed them back. A queue's occupancy matches its pointers; a state vector is one-hot; an outstanding counter never exceeds capacity. The only kind of assumption that costs nothing, because you have discharged it.
5Case-split, once you have shown those configuration values partition the space — N results, and the plan row must say so.
6Abstract — last of the model-changing moves, because the deletion list comes with it.
7Accept a bounded result, with the depth recorded and its antecedent covered under the same bound.
8Stop. Hand the plan row to simulation and close it there.

Four of them — rewrite, lemmas, case-split, abstract — change the problem instead of answering it, and return you to the top with a smaller one. Step 8 is a legitimate outcome, not a defeat: a team that cannot reach it will spend a whole schedule on one property.

Formal Apps and Equivalence

Formal packaged as a product rather than practised as a craft — and the checking flows that have run quietly on every project for decades.

A HOLISTIC GUIDE26

Chapter 15 · The opening scenario

The interrupt arrives on input 5. The header says input 6.

Two thousand lines of instantiation and wiring at the top level, containing one mistake. Both blocks are correct, so every block-level environment passes. The system regression passes too, because no test both provokes an accelerator error and enables that particular interrupt: the error path is exercised by the accelerator's own tests, which read the status register, and the interrupt map by the event unit's tests, which inject events directly.

It surfaces in the lab, as a hangNothing here is subtle. The intent is a table with a few hundred rows — this source, that destination, under this condition — and the implementation is structural wiring. Comparing the two is mechanical, and answering it by simulation is absurd: one directed test per row, each proving a single wire, none exhaustive over the conditions.
Meanwhile the team's one formal specialist is unavailableShe is three weeks into the crossbar's ordering proof, choosing abstractions and defending assumptions. She is also not needed. This question requires nobody to write a property. It requires a tool that already knows which property to write, and a table to write it from.

SayEvery integration bug of this shape survives block-level verification by construction, because every block is correct.

A HOLISTIC GUIDE27

Chapter 15 · The app

The tool brings the properties. You bring the design and a configuration.

Chapter 14's flow is mostly specification work — read the spec, decide what is worth proving, write properties, state and defend assumptions, fight convergence. Only one of those steps is the engine's. An app inverts the economics by shipping the properties: an X-propagation app reads the RTL and implements the assertions itself. Nobody writes a property or states an assumption.

Chapter 15 · Connectivity checking

Proving the wiring — the highest-value, lowest-effort app on most projects

// Intent row: src = nn_err_irq, dst = evt_in[6],
//             enable = cfg_irq_en[6], latency = 1 cycle.
property p_conn_nn_err;
  @(posedge clk) disable iff (!rst_n)
    cfg_irq_en[6] |=> (evt_in[6] == $past(nn_err_irq));
endproperty
a_conn_nn_err : assert property (p_conn_nn_err);

The antecedent is the enabling condition sampled now; the consequent fires one tick later and compares the destination against the source as it was when the enable was true. It says nothing about cycles where the enable is low — an unconditional claim would be wrong. Two hundred rows of this, generated and discharged in one run, is the entire flow.

One of the two hundred is the row aboveIt does not prove: the wiring reaches input 5. No test had to provoke an accelerator error while that interrupt was enabled — the proof does not care whether one ever would.
The dual claim, and the part teams forgetA table listing what must be connected says nothing about what must not be. On the crypto engine: no path from any key-ladder output to a bus-readable address, the debug data register, or a scan-observable point. Cheaper still — a structural question a tool answers without a proof engine getting involved.
But be exact about what a negative row provesA no-connection result is structural: no path exists. It does not say the key never influences an observable value along a path that does exist — that is an information-flow question. Confusing the two is how a team believes it has proved non-leakage when it has proved non-adjacency.

Scaling. Make the port indices symbolic — an arbitrary manager and subordinate, constrained only to be stable — and one property covers every value they could take. Not always faster: 162 seconds symbolic against 65 for the exhaustive per-path proofs together.

Chapter 15 · Register checks

The map against its description — and the gap it does not close

One register description generates every view a project already has and already lets drift: RTL decode and field logic, verification model, firmware header, documentation. The app closes the remaining edge — it proves the RTL implements the description, per register and per field.

A conventional register test walks the map front-door, pattern by pattern — which is why a large map's register test is measured in hours. The app proves the same statements over all values and orderings, at RTL rather than through the bus.
Two of those arguments are exactly what the app is for"W1C" is a statement about every possible write value and both possible current values, of which a random register test exercises a handful. And volatile records that hardware can change the field without software's involvement — so the check must read a software write of 1 clears the field unless hardware sets it in the same cycle, not the field is 0 after the write. An app that ignores the flag generates a check that fails on correct hardware, and the first thing a team does with a failing generated check is switch it off.
Now the honest limitThe app proves RTL against description, and the register model and the RTL check come from the same file: a common-mode error, encoded once and read twice. Nothing here reviews whether bit 3 was the right bit. That review is a human reading the description against the architecture document — and the app's value is that it removes everything else.

Scenario — the GPU's four shader clusters carry identical register banks; cluster 3 is hand-edited during a late change and one counter's reset value is left at the previous revision's. The app enumerates from the description, so it checks cluster 3 whether or not anyone thought about cluster 3.

A HOLISTIC GUIDE30

Chapter 15 · Unreachability

A proof instead of a waiver — and what the verdict inherits

A coverage exclusion's reason is almost always an engineer's claim that a state is unreachable. That is a reachability question about the design, and reachability is what a model checker computes: what was an opinion in a waiver becomes a result in a database.

Catch one — the word legalReachability is computed relative to the constraints, and a wrong constraint makes reachable behaviour look impossible. One case is worth memorising because it is so ordinary: an input constraint hiding in a tool setup script, enable_cnt == 0, made a counter's increment line uncoverable. It was reported unreachable, and it was — under an assumption nobody had reviewed.
Catch two — it works on the designRTL lines, branches, FSM states, cover properties bound into design scopes. A functional coverage model computed by the testbench is invisible to it.
 
// Can the midend ever emit a full-length burst out of a
// transaction it had to split at a 4 KB frontier?
c_split_max_len : cover property (
  @(posedge clk) disable iff (!rst_n)
  midend_txn_done && midend_did_split
  && (midend_burst_len == 9'd256));

The canonical DMA cross x_worst has 72 combinations. Six — the whole straddle × max column, 3 stride signs × 2 other-channel states — are excluded by the generator's c_solver_budget, a budget the team chose. That leaves 66 cells to close.

The engine answers in seconds — and the cover is REACHABLENothing in the design bounds a descriptor row at one maximum burst. The bound that empties the column lives in the constrained-random generator, and a design-level cover does not inherit it.

Be precise about what that does and does not overturnThe exclusion is not refuted. What is refuted is its type. It looked like a statement about the design and it is a statement about the stimulus — true while the generator stays as it is, false the morning someone widens it. So the disposition stays a waiver, and this is what its expiry field is for: the expiry is an edit to the constraint file, which nobody counts as verification evidence until the morning it is.

A HOLISTIC GUIDE31

Chapter 15 · Auto-generated properties

A draft, not a specification

Point this app at the RTL and it extracts implementation-detail properties — interface handshakes, one-hot encodings, occupancy bounds, the structural invariants a designer would state if anyone asked. No table, no description, no configuration beyond a module name. Judged by the intent column it is the cheapest row in the catalogue: the intent source already exists, and it is the design.

Which is exactly what is wrong with itEvery other app reads intent from something that is not the design — a wiring table, a register description, a coverage model — and the gap between the two is where the app finds bugs. This one closes the gap by construction.

The limitation is structural rather than a matter of tool maturity: mining generates and evaluates its properties on the same RTL with no golden reference to appeal to, so flaws in the RTL yield flawed properties and the method has nothing with which to notice.

Follow that throughA mined property cannot fail on the RTL it was mined from. It proves — and it would have proved on a design with the opposite behaviour, because the behaviour is where it came from. Its bug-finding power against today's RTL is zero, and no amount of proof depth changes that.
What it is worth is what a regression is worthIt converts the design's present behaviour into an obligation, so the next edit that changes that behaviour has to argue with something instead of sliding through.

The review question for each of three hundred generated properties is not is it true — it is, by construction — but is it intended, and answering that is specification work, property by property, done by the specialist the app was supposed to make unnecessary. An app that emits verdicts removes that work. An app that emits drafts relocates it. Budget the review, or do not run the app.

Scenario — the inherited UART, four years old, specification lostIts RX overrun flag is never cleared when software reads the status register in the same cycle a stop-bit error arrives. The RTL exhibits it, so a mined property states it as an obligation — and the day someone fixes the bug, the property fires as a regression. A generated set encodes the design's defects with exactly the fidelity it encodes its features.
A HOLISTIC GUIDE32

Chapter 15 · Equivalence checking

The flow's quiet workhorse: a design against another design

Every technique so far compares a design against a specification. This compares a design against another design — weaker-sounding, worth more, because the flow's most frequent transformations are ones nobody verifies any other way. Chapter 2's reconvergence model: synthesis turns RTL into a netlist, equivalence checking is an independent second path from the same origin, and the two reconverge at a proof that the transformation preserved functionality. No stimulus, no coverage, no oracle problem.

LEC — and its assumption is the whole storyIt does not reason about sequences. It matches state points — the registers of both models — one-to-one, then proves the combinational logic computing each is Boolean-equivalent. Everything follows: fast, exhaustive because it never enumerates a trace, and it degenerates into a mapping problem when the state points do not match.

It keeps the synthesis tool honest. The canonical illustration: a design synthesised incorrectly from a synthetic arithmetic operator whose documentation said correctness was not guaranteed above 48 bits — documentation the synthesis tool could not read. Equivalence checking found it quickly; gate-level simulation with great difficulty, if at all.
SEC — drops that assumption and pays for itEquivalence now means every input sequence produces the same output sequence, decided on a product machine running both designs in lock-step. That is a model-checking problem, with model checking's costs — so it is aimed at bounded, well-chosen transformations rather than sprayed across a design.

Clock gating. Gates inserted on the accelerator's 16-lane MAC datapath: if the condition is wrong by one cycle the datapath holds a stale value that surfaces only on a weight-stream boundary. Retiming. The radar front-end's FFT pipeline misses timing, a stage boundary moves — same arithmetic, different register mapping, so LEC will not map the state points at all.

And one row holds across LEC, SEC and the datapath flow alike: what each is blind toWhether the reference itself is right. Equivalence is a relative argument: it transfers your confidence in one model onto another exactly and without loss, and it transfers your errors with the same fidelity. Nothing here says the RTL is correct. It says the netlist is as correct as the RTL — a smaller claim, and the one the flow actually needs.

A HOLISTIC GUIDE33

Chapter 15 · Datapath

Where simulation's coverage argument does not degrade — it collapses

The clean case: a codec's inverse transformAn 8×8 residual block is 64 coefficients; at 16 bits each, the input space of a single invocation is 21024 values. No coverage model samples that meaningfully, and no argument from “we ran a billion random blocks” survives contact with the arithmetic.

Worse, the failure mode is not a region of the space but a scatter — a rounding term applied at the wrong stage, a saturation clipping one bit late, an intermediate width one bit short. Each is wrong for a sparse, structured subset of operands that random stimulus meets with probability near zero. And the standard specifies the transform as exact integer arithmetic, so a one-bit mismatch in one coefficient is a conformance failure, not a quality issue.
What makes it tractable: the specification is not proseIt is a mathematical relation between operands and result, and it can be written as one. The pattern established after the floating-point division episode: state a multiplier's top-level specification as a formalisation of the arithmetic standard, with significand and exponent read as integer values rather than bit vectors.

And decompose: over 120 properties covered all arithmetic operations of one industrial floating-point unit, each a property about a subunit, with the irrelevant parts extracted away per property. Two lessons carry: reason at word level, not bit level, and the monolithic claim does not converge.

Scenario — the radar front-end's CFAR detector, and the comparison nobody asks forDatapath verification proves the RTL bit-exact against the algorithm team's fixed-point C model, on every operand. Ship it — and then run the other comparison: the fixed-point model against the floating-point one, over the operating envelope, with a declared error bound. Bit-exactness against the fixed-point reference is a complete answer to did we build the model correctly and no answer at all to is the model adequate. A detector that saturates on a strong near-target loses a weak far one, and every stage of the equivalence argument passes while it happens.

Chapter 16 · Assumption and constraint duality, as a flow

One interface rule lives three lives — and the dangerous drift is silent

GENERATOR CONSTRAINTa predicate over a randomized object — produces legal traffic on the block's input
ASSERTIONa predicate over a signal history — checks legality on the neighbour's output
ASSUMPTIONthe same text, deleting traces from a formal model

These are not one statement in two syntaxes. So no tool diffs them, and no compiler complains when they diverge. Teams discover the divergence at sign-off, or never.
Drift one — the generator is narrower than the assumptionThe formal environment permits traffic the tests never send. This is sound: the proof covers a superset of what simulation exercised, so nothing is claimed that is not established. And it shows up honestly, as a coverage hole on the simulation side.
Drift two — the assumption is stronger than the generator's legal setThe proof holds over a subset of the traffic the tests actually send — so simulation is exercising behaviour the proof never covered, while both reports are green. Nothing on either side is empty. There is no hole, no failure, and no artifact anywhere that records the gap.

This is Chapter 14's quiet over-constraint arriving through a second door: not an assumption written too strong for the design's environment, but one written accurately for an older environment that the stimulus has since outgrown.

Chapter 16 · Two detectors

Make the assumption the source of truth — it is the one whose failure is silent

module wake_handshake_checker #(parameter bit ASSUME_MODE = 1'b0) (
  input logic clk_slow, rst_n, wake_req, wake_ack
);
  // The requester may not withdraw an unacknowledged request.
  property p_req_holds_until_ack;
    @(posedge clk_slow) disable iff (!rst_n)
    (wake_req && !wake_ack) |=> wake_req;
  endproperty
  c_req_waited : cover property (@(posedge clk_slow)
                   disable iff (!rst_n) wake_req && !wake_ack);
  if (ASSUME_MODE) begin : g_env
    m_req_holds_until_ack : assume property (p_req_holds_until_ack);
  end else begin : g_chk
    a_req_holds_until_ack : assert property (p_req_holds_until_ack);
  end
endmodule

Read the property before believing anything about it. It says only that an unacknowledged request survives into the next cycle — nothing about life after wake_ack rises, and it never constrains wake_ack.
Detector one — compile the assumption set into simulation as assertionsWhen the DSP's wake controller is proved, wake_req is an input and the instance is built with ASSUME_MODE = 1. When the island is proved, the same text is asserted. And bound into the DSP's own block-level simulation, where wake_req comes from the testbench, that instance is checking your generator, not the design. If a sequence ever drops an unacknowledged request it fires, naming the assumption that would have been silently violated in formal — on a nightly run rather than at sign-off.
Detector two — cover the assumption's boundaryDetector one catches the generator going outside the assumption. It says nothing about the commoner case: staying so far inside that the assumption was never tested. If c_req_waited reads zero, the assertion has never evaluated non-vacuously. Every assumption ships with a cover on the condition it restricts.

Together the two turn Chapter 14's assumption register from a reviewed document into a monitored one — each row gaining a column for its assertion's last pass and its cover's last hit.

Chapter 16 · Coverage unification

What a unified report may claim, and what it may never

A simulation bin holds a count: this situation occurred, n times, in the runs I performed. A proof holds a claim: no legal trace violates this rule. They are not two measurements of one quantity — one is a statement about your testbench and the other about your design. Average them and the percentage has a denominator made of two incompatible units.

Merges in one unitTravels as a tagged item, with its qualifiersMust never be summed
Code coverage — lines, branches, conditions: formal reachability and simulation report hits against the same structural denominatorAn assertion's result plus its radius — a bounded proof's depth or a counterexample's length — with the assumptions, abstractions and cutpointsFunctional bins against proofs. The standard's own caution on heterogeneous mergesSuch items are more often semantically different than equivalent, so they should not be merged automatically; a tool that does must record the result as a new item carrying a semantic tag saying it is merged data. The merging algorithm itself is left unspecified. A licence with a condition attached.
And a percentage is a property of a model, not of a designAn eight-bit variable that took the values 17 and 96 scores 2/256 under a metric with one bin per value and 2/8 under eight-bin auto-binning. Collection loses information that cannot be recovered afterwards — and it compounds when the denominators come from two engines that never agreed on a partition.

Chapter 16 · The reconciliation

Unify at the verification plan, not at the coverage database

The honest answer is not a better merge algorithm. Chapter 5's one-row-one-metric rule was written for exactly this: a row discharged by a proof closes on the proof — with its depth, its assumption list and its own formal coverage evidence — while a row discharged by a covergroup closes on the covergroup. Nothing has to be averaged, because nothing was ever a fraction of the same whole.

What the dashboard reportsRows closed out of rows planned, per engine and in total — a number with a denominator anyone at the review can name.

That is also the honest form of “proven, so no coverage needed”: the row needs no functional bin, because the proof discharges what the bin was sampling towards — and it still owes the formal coverage models, which is why a proof never closes a row on its own.
Job one — structural coverage, in one unitFormal reachability produces line, branch and condition coverage in precisely the units simulation uses, so those genuinely add. On a published multicast crossbar of eight clients and eight targets, the completed formal testbench alone covered all 288 lines and all 88 conditions, deepest cover point at depth 5 — inside that project's derived required proof depth, which the authors take as evidence the depth is not optimistic.
Job two — the tripwire teams leave switched offAn item can be flagged formally unreachable, and the classification separates a don't-care from a predicted-unreachable point precisely so a warning is raised if it is later covered. Chapter 15 turned a waiver's argument into a proof; this makes the proof a live tripwire.

And the failure worth naming, because it looks like progressWriting a proof's verdict into a functional bin destroys two instruments at once. The bin's job is to record what the stimulus did: overwrite it and the fresh-seed yield no longer discriminates a converged suite from a saturated one, while the coverage differential can no longer fail a commit that quietly made the suite ask less. You have not gained coverage. You have blinded two metrics to buy a number.

Chapter 16 · Choosing an engine

A decision procedure a lead can apply in a plan review — per row, not per block

1Does the criterion quantify over all traces, or over a traffic profile? Profile criteria stay simulation rows however elegant the property would look
2Is the interesting behaviour a corner or a volume? A conjunction of rare conditions goes to formal even when the block is large, because the abstraction that makes it converge usually preserves the conjunction
3Can the block's environment even construct the witness? If not, the row is not a stimulus-tuning problem
4What does the row's model have to contain? Price the abstraction bill and the deletion list before committing
5Who owns sign-off for this row? Sometimes the answer is nobody on your project
6What happens if it does not converge? Answer this in the plan review, not in week nine
Question five — the USB controller's link-training rowsThe U0 through U3 transitions are as good a formal target as exists, and a proof of them is cheap, fast and finds real bugs. Run it, and do not let it close the rows — their closure metric is the compliance suite's item list. Cheaper but not sufficient for sign-off is not a criticism of formal: the proof is stronger evidence than the suite for the rules it covers. It is a statement about who holds the authority to declare the row done.
And the outcome that looks like waste and is not: bothOne deployment began its formal effort after a major dynamic-verification milestone had completed, on designs whose simulation environments were already stable — precisely where a second method should find nothing — and reported 82 interesting bugs over twelve weeks. The taxonomy is the useful part: easy, a state machine attempting two arcs at once; medium, counter overflows and arbiter starvation; hard, a deep internal counter value coincident with a specific input sequence. Even the easiest would have been difficult for the running environment to find.

Chapter 16 · The handoff

Artifacts crossing between two engineers — and what must travel with each

Formal → simulation

A counterexample becomes a directed testThe trace is near-minimal, so the test is short, and it is exactly the stimulus a random generator was demonstrably not producing. Travels with it: the property it violated, so the failure condition is the assertion rather than a hand-written expectation — and a cover on the scenario, so a later constraint change that quietly stops reaching it is visible.
An unreachability proof becomes a waiver's justificationTravels with it: the constraint set, as evidence, reviewed as seriously as the waiver it replaces — plus the flag on the coverage item that warns if the point is ever covered later.
An assumption becomes a checkerThe most valuable of the three, because it runs every night. Travels with it: the assumption register row it discharges, and the boundary cover.

Simulation → formal

A coverage hole becomes a reachability questionA hole that has resisted three targeted tests is the classic candidate. Two of the three outcomes are decisive: a witness hands the stimulus engineer a recipe, and unreachable converts the hole into an exclusion with a proof behind it. Inconclusive leaves the hole exactly where it was — worth knowing before spending a week on it.
A long failing trace becomes a propertyFormulating the violated rule and running a bounded proof often returns a counterexample an order of magnitude shorter. Travels with it: the seed and run manifest of the original failure — the short trace is a different execution, and someone must confirm it is the same bug.
A redundant-state invariant becomes a lemmaExactly the facts a proof engine must be told to stop generating impossible starting states — and they cost nothing to hand over, because they are already written and already believed.

Staffing follows from the list: every handoff here needs someone who can read both kinds of report, so a project with exactly one such person has a bottleneck rather than a hybrid flow.

Seven sentences worth leaving with
  • A static gate is exhaustive over structure and silent about function: why it goes first, and why it is never the whole story.
  • One bit needs metastability fixed; several bits need metastability and coherency fixed.
  • A proof is a statement about a model, under assumptions, sometimes to a depth. Without those three it is a mood.
  • A missing assumption arrives in red; an extra one announces nothing. Review the assume list, not the checkmarks.
  • A bounded pass says the property cannot be violated too soon: carry the depth, and cover the antecedent under it.
  • An app relocates the specification, it does not remove it — and one that mines the design proves by construction.
