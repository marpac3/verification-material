Every technique must discharge a named verification claim.

Establish the static boundary→Qualify the proof→Choose the application
    HARDWARE VERIFICATION LESSON 41

    Open with a decision the audience must make in this area. Ask which result they currently treat as sufficient evidence and keep that answer for the closing discussion.

    The lesson selects a practical argument from the book. The study handout preserves the detailed examples, citations and worked artifacts.

    Learning outcomes

    Demonstrate these decisions on a real plan row.

    • Separate structural results from protocol obligations.
    • Qualify a proof by assumptions and abstraction.
    • Distinguish generated intent from independent checking.
    • Combine typed results through a verification plan.

    At closure, require a concrete artifact or explanation for an outcome rather than a general expression of confidence.

    Static and formal verification

    Static results have a subject

    Structural cleanliness does not establish functional correctness.

    Structure→Rules and waivers→Remaining behavior
      HARDWARE VERIFICATION LESSON 44

      Use lint to remove avoidable structural ambiguity before spending simulation or proof effort. Ask which failure classes the selected rules actually detect.

      A clean report says nothing about a missing specified feature unless that feature has an independent check. Keep rule configurations and waivers attached to the result.

      Static and formal verification

      Synchronizers do not define a protocol

      Independent bit crossings do not guarantee a coherent word.

      • Review the crossing structure.
      • Then review data stability, capture and handshake behavior.
      HARDWARE VERIFICATION LESSON 45

      Draw a multibit value whose bits can be observed from different source updates. Individually synchronized bits do not make those updates atomic.

      The structural CDC result and the protocol obligation need separate evidence. Ask what guarantees the data is stable during the destination’s capture window.

      Static and formal verification

      Reset and unknowns need their own review

      A clock-domain inventory does not enumerate reset hazards.

      • Inspect reset assertion and release interactions.
      • Separate X optimism from X pessimism.
      HARDWARE VERIFICATION LESSON 46

      Explain why reset interaction can cross boundaries even where clocks are shared. Do not infer RDC closure from a clean CDC report.

      An unknown that disappears optimistically and one propagated pessimistically call for different diagnoses. The simulation configuration is part of the interpretation of the result.

      Discussion: a clean crossing report

      Name the evidence that would settle the decision.

      • A multibit status uses independent synchronizers.
      • The structural report is clean.
      • What coherent-transfer claim still needs evidence?
      HARDWARE VERIFICATION LESSON 47

      Expected answer: the receiver must observe a value that corresponds to a permitted source transaction, not an arbitrary mixture of updates.

      Ask for a protocol argument and its checker. Neither the absence of a structural warning nor the name of a synchronization cell supplies that argument.

      A proof verdict is a qualified statement

      Property, model and assumptions travel with the result.

      Property→Model and assumptions→Qualified verdict
        HARDWARE VERIFICATION LESSON 48

        Have a learner say the complete claim aloud: which property, over which model, under which environment assumptions. A green result without these qualifiers cannot be transferred to a plan row.

        Ask which legal behavior an assumption removes. A restriction introduced only to make convergence easier needs independent review before its proof can support sign-off.

        Static and formal verification

        A bounded pass has a boundary

        State the depth and justify what lies within it.

        • A counterexample is a concrete failing trace.
        • A bounded pass needs a depth argument.
        HARDWARE VERIFICATION LESSON 49

        Contrast finding a failure within a bound with establishing absence of failure beyond it. The latter does not follow automatically.

        The chapter combines latency and scenario analysis, cover witnesses and prior counterexamples. Review completeness of the scenario enumeration as well as its arithmetic.

        Static and formal verification

        Abstraction changes the trace set

        Know which conclusion survives the reduction.

        • Adding behavior can preserve proofs but introduce false failures.
        • Removing behavior can preserve failures but hide real ones.
        HARDWARE VERIFICATION LESSON 410

        Use over-approximation and under-approximation explicitly. Explain why admitting extra traces makes a successful universal proof stronger while a failure may need validation against the concrete design.

        Conversely, restricting traces can make a discovered failure useful without making a pass exhaustive. Record deleted behavior and the plan rows that cover it elsewhere.

        Discussion: assume away the failure

        Name the evidence that would settle the decision.

        • An ordering property proves after adding an assumption.
        • No owner can justify that environment restriction.
        • Can the row close?
        HARDWARE VERIFICATION LESSON 411

        Expected answer: the result does not discharge the original unrestricted claim. Review or withdraw the assumption, then obtain evidence for the remaining legal behavior.

        The chapter’s assumption register distinguishes proven premises, simulation checks and accepted arguments. An undocumented convergence aid belongs to none of those categories.

        Static and formal verification

        Automation still needs reviewed intent

        Generated properties inherit their source description.

        • Connectivity and register checks scale repetitive obligations.
        • Review the description that generated the checks.
        HARDWARE VERIFICATION LESSON 412

        A connectivity specification or register description lets the tool generate many mechanical checks. The engineer still decides whether that description captures the intended connection or side effect.

        Generation can eliminate transcription drift while preserving a shared error in the source. Ask which review or independent evidence can expose that shared error.

        Static and formal verification

        An inferred property is not an independent oracle

        Mining a design can reproduce its mistake.

        • Label the origin of generated properties.
        • Compare design-derived claims with external intent.
        HARDWARE VERIFICATION LESSON 413

        Distinguish elaborating a reviewed specification from discovering patterns in the implementation. Both may produce useful properties, but they have different independence.

        A property that faithfully describes current RTL can hold while the RTL violates its specification. Keep that distinction visible when admitting the property into a closure argument.

        Static and formal verification

        Equivalence inherits the reference

        Preservation and correctness are different claims.

        • Define the correspondence and transformation boundary.
        • Choose sequential reasoning when state alignment changes.
        HARDWARE VERIFICATION LESSON 414

        Use a combinational transformation and a retiming change to expose the difference between matched-state comparison and sequential equivalence.

        A successful comparison supports preservation within the configured model. It cannot independently establish that the reference was correct, nor that excluded modes behave acceptably.

        Discussion: generated from one source

        Name the evidence that would settle the decision.

        • The register RTL and its checks share a description.
        • All generated checks pass.
        • Which error can both artifacts share?
        HARDWARE VERIFICATION LESSON 415

        Expected answer: an incorrect or omitted behavior in the source description can be reproduced consistently in both artifacts.

        Ask for the external specification review or independent check that would expose it. A second generated artifact is not automatically a second interpretation of intent.

        Static and formal verification

        Allocate engines per claim

        A feature name alone does not select a method.

        • Match the oracle, state space and runtime need.
        • Keep each result attached to its plan row.
        HARDWARE VERIFICATION LESSON 416

        Take one DMA feature and separate an invariant, a functional transfer and a long software scenario. They can need different engines and evidence boundaries.

        The plan should explain why each engine answers the particular row. Do not choose a method merely because a tool or platform is available.

        Static and formal verification

        Check the formal environment in simulation

        An assumption is a promise that another boundary must honor.

        • Turn relevant premises into simulation checks.
        • Cover important boundary behavior.
        HARDWARE VERIFICATION LESSON 417

        The same expression can restrict a formal environment and monitor the actual integration environment. Explain why these are complementary uses with different verdicts.

        A simulation check observes sampled executions; it does not prove the environment universally. Record that scope when discharging the formal assumption.

        Static and formal verification

        Keep coverage evidence typed

        Simulation activity and formal coverage have different denominators.

        • Unify the plan, not unrelated percentages.
        • Handoff assumptions, exclusions and unresolved traces.
        HARDWARE VERIFICATION LESSON 418

        Ask what an average of a functional bin percentage and a proof-core percentage would mean. There is no shared population to support that aggregate.

        Use the plan row as the common unit. A handoff must retain the exact residual claim and its model restrictions so that the receiving engine does not unknowingly check a weaker problem.

        Discussion: the blended dashboard

        Name the evidence that would settle the decision.

        • A dashboard averages simulation and formal coverage.
        • The resulting percentage rises.
        • Which closure argument is still missing?
        HARDWARE VERIFICATION LESSON 419

        Expected answer: the mapping from each typed result to the intended feature claim, with its own denominator and limitations.

        Require the presenter to name what newly became established. A rising arithmetic aggregate cannot answer that question by itself.

        Exercise: coverage or mutation sensitivity?

        Choose an instrument for the actual question.

        • Proof-core coverage is offered as arbitration-change sensitivity.
        • Explain the gap and choose the appropriate instrument.
        • Include the chapter’s recommended proof-core scope.
        HARDWARE VERIFICATION LESSON 420

        Exercise 14.4 (judgement). A team offers proof core coverage, run over every property in its suite, as evidence that the property set would notice a change to the crossbar's arbitration logic. Decide what the four coverage kinds of §14.6 establish as a class and what none of them establishes, and name the instrument §14.6 assigns to the question the team is actually asking. State the scoping §14.6 gives for proof core analysis, with the two reasons it gives for that scoping.

        Assign book Exercise 14.4 in full. Review the four coverage kinds before the learner selects an instrument.

        Expected answer: coverage measures aspects of exploration or the proof’s relation to implementation; none establishes that a property set detects a meaningful design mutation. Mutation analysis addresses that question. Explain the chapter’s selected proof-core scope and its cost and interpretation limits from the reading. Scope proof-core analysis to a handful of highest-value properties: it has the highest computational cost and its vendor-specific metrics are harder to interpret.
